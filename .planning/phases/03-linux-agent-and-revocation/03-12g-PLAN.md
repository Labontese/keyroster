- **What exit 4 means in operation.** A signer restore that brings an older trust bundle back makes every automation account that has the managed file exit 4 on every run until the root signs a newer bundle (the refusal is right: such an account cannot learn a new host CA then); and a managed file that someone edited by hand, or that holds CRLF line ends, gives exit 4 on every run until an admin's sync rewrites it. machine-identities.md says both (B11, P37).

## Planner decisions (Claude's discretion), recorded with their reasons

- **Where the names come from: read back from the file's own CA lines, strictly.** Three sources were open. (a) `host-trust.json`'s names are every name the client ever saw (cmd/keyroster/knownhosts.go:203-216), so CA lines over them would bring disabled and removed names back, against enroll-user.md item 4 (:646-651) and `TestHostCertNoTOFU/refused_through_missing_ca_line_alone`. (c) A new state field means format 2, and an older CLI then refuses the state and every write (`st.Format != 1`, knownhosts.go:243-244) until the files are deleted. (b) The managed file's own CA lines carry exactly the names the last full refresh gave a host CA, and the owner's chosen text describes this source ("for the host names the account's file already trusts"). The rule: a line is a source line when its first field is `@cert-authority` in any letter case (the narrowing's classifier, narrow.go:259-268), it has at least four fields, and fields three and four, joined by one space, are the key of a host CA the verified bundle trusts at the client's clock (`trust.TrustedCAs`); every source line must be byte for byte what the writer writes for its names and that CA (`hostCALine(names, ca)`, which knownHostsFile uses, knownhosts.go:851-856), its names must each pass `hostTrustName` (knownhosts.go:155-171) and be sorted and unique, as the writer writes them (`hostTrustNames`, :182-201); all source lines must carry the same names. A line of an untrusted key is ignored (it is the narrowing's to remove; the narrowing may have declined), and a file with no source line gets nothing (no bootstrap). Any source line not in the writer's form, or source lines that disagree, fail the step: never a union, never an intersection. The new line's key and generation come only from the root-verified bundle; the file gives names only. Whoever can write that file can already add any line to it, so reading names back from it grants nothing that writer did not have (T-03-465, T-03-466).
- **What it adds: active and next host CAs only.** The step adds the line of each entry of `trust.IssuingCAs(b, host)` (internal/trust/castate.go:22-43: active and next, in generation order) whose key has no source line. It never adds a draining entry: a draining host CA was active before, so a file the writer wrote already holds its line, and re-adding one would undo a narrowing after a clock step back. This is the owner's "the new host CA's line" for each of the cases of a rotation: current plus next (after ceremony 1) adds the next line; current plus draining (after ceremony 2, for an account that missed the window between the installs) adds the new active line beside the old one; one host CA adds nothing. A file whose every line the narrowing removed (an account that ran nothing between ceremony 1's install and the old host CA's drain end) has no source line and gets nothing; that account needs an admin's sync, like every account that missed the gate.
- **A path of its own, not the writer's no-directory branch.** `writeHostTrust`'s branch without a directory (knownhosts.go:532-556) is shared by sync and login and pinned by exact output and exit 3 (knownhosts_test.go:1248, `TestKnownHostsSync/sync_exit_3_when_partly_refreshed`, among others); putting the addition there would change what sync and login do and need the KRL fetch. The step is `machineHostTrust` in its own file and has one caller. The side effect "a login whose answer missed the directory then also gains the new line" is left out: it would change login's writer output and its pins. Recorded as a later item ("Cross-plan notes").
- **What it reads, and when it runs.** The host CA keys are in the bundle `verifiedTrust` already fetched and verified (machinerenew.go:112). The step makes no request of its own, so it depends on neither the KRL route nor its shared limiter. It does not refresh revocations: an automation account's `keyroster_revoked_hosts.krl` still changes only on an admin's sync, and the runbooks say so. It runs once, right after `verifiedTrust` returns, before the policy check, the key read, the `--if-due` decision and the renewal request, so every run adds the line, a not-due run and a refused renewal included: the gate needs the line before the account's next ssh, so the runbook's bound is the interval between the account's runs in the installation's own terms, never the example cron line, which machine-identities.md labels UNVERIFIED (:149).
