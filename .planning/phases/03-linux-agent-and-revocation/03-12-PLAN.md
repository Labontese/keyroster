<objective>
The signer holds every CA key as a numbered generation that the audit log records, refuses to start when the generations and the log disagree, and refuses every writer of its state while a restored database has not been recovered or ruled out. This is the first of six plans that build D-14 and KEY-08, CA rotation through a `next` CA and a "draining" CA with no failed logins. It is published together with its five successors and changes nothing that a host, a client or a trust bundle can observe.

Purpose:
- **Generations.** A rotation first needs a key that exists, is recorded and can be addressed. Today the signer knows one key per role (ca_keys, loadTrust, checkStoredTrust, Backend.Key by fingerprint with one file per role). This plan adds the table, the leaf, the prepare command and generation-addressed key opening, while checkBundleKeys admits no CA entry that d15f044 refuses, so a hand-made root-signed successor still cannot change a CA entry.
- **The restore gate.** `ca-rotate prepare` is the first offline command that writes the log, and any install, prepare or serve under a restore hold forks the prepared recovery. One marker, checked at the one choke point every state writer passes, closes that.
- **The issued_at refusal.** The ceremony clock is offline and unbounded (trust/verify.go:373-377 bounds a bundle only by its predecessor). A bundle dated far ahead would stretch a later drain or block every later successor; the install refuses it now.
- **Requirement.** KEY-08 (pending). This plan advances it; it completes in 03-13 with the log and ops keys.

Output:
- migration 0006, the kind-14 leaf with its vector, registry row and fuzz targets;
- keystore generation interfaces, software generation files, `PrepareGeneration` and `keyroster-signer ca-rotate prepare`;
- the start-up and doctor cross-check, generation-based bundle-key checks, the audit rules and export;
- the restore marker, its release paths and `--migrate-only`, the install refusal and the doctor facts;
- the runbook text, the registry row, the publication of all six plan files with the wave shift and the pointer edits, and a PR.
</objective>

## Planner decisions (Claude's discretion), recorded with their reasons

- *Generation addressing is an optional interface.* `keystore.GenerationBackend { KeyAt(role, generation, fingerprint, location) }` is implemented by the software backend only, and `keystore.KeyFor(be, role, generation, fingerprint, location)` calls it when the backend has it and `Backend.Key(role, fingerprint)` otherwise. `location` is the generation row's location column: `GenerationProvisioner.ProvisionGeneration(role, generation, used)` receives the non-empty locations that every stored row of every role records and returns `(pub, location, err)`, PrepareGeneration stores the returned location, and loadTrust passes each row's location to KeyFor. The software, agent and memory backends ignore the argument (software returns an empty location). 03-12f's PIV slot, and the handle of any later backend, therefore needs no new interface: the allocator sees what is used, the row carries what was chosen, and KeyAt and 03-12e's Holds receive it. The agent backend already selects by fingerprint, memBackend (internal/signer/log_test.go:36) ignores the role, and the tpm and piv backends keep their genesis key files until 03-12f, so none of them is edited. A request for generation 2 on a backend without the interface falls back to Key, which compares the fingerprint and refuses (it never falls back to another key, keystore.go:58-64).
- *The state lock keeps its signature.* `lockStateDir(stateDir)` (cmd/keyroster-signer/lock.go:28) checks the marker after it takes the flock and releases the lock when it refuses. A second function, `lockStateDirForRecovery`, shares the body and skips only the marker check; recover-revocations is its only caller, in its three forms (the recovery, `--no-recovery-needed` and `--migrate-only`), and under the marker it is the only command that opens signer.db for writing. serve.go:87 and openState (serve.go:230) are therefore not edited, and TestStateDirLock keeps its calls. A future command that opens the state through openState inherits the gate and cannot forget it.
- *The marker is written by the file-restore block, not by the hold block.* signer-install.md uses the hold block for backups too ("Taking a file backup"), so a marker written there would block serve after every backup. The file-restore block runs only on a restore, after the lock check and before signer.db is replaced. The hold, file-restore and release blocks are pinned character for character in three places: the runbook, restoreFilesScript in test/e2e/restore_test.go and file_restore() in test/systemd/smoke.sh (TestRestoreRunbookChecks). They change together, in Task 3. smoke.sh also gains the marker's lifecycle (written by the block, kept by a refused recovery, reported by doctor, cleared by `--no-recovery-needed` before the hold is released), so the systemd-sandbox job runs it. An earlier draft put the marker in the hold block; that would have broken the three pins and every backup.
- *Audit requires a logged generation for every `next` entry, and for every active CA entry once a ca_init leaf precedes the install.* No audit fixture at d15f044 writes a ca_init leaf before a bundle_install (newFixtureAt, internal/audit/verify_test.go:129-134 starts at the bundle_install), and phase1_kinds_still_verify (:1470-1484) appends a ca_init after the bundle with one key that is not even a parseable key. An unconditional rule "every active entry equals a logged generation" would fail dozens of tests and the FuzzVerifyExport seeds. So ca_init keys are recorded without being refused; the ca_generation chain rules are enforced; every `next` entry must equal a logged generation (vacuous until 03-12b); and at a bundle_install that comes after a ca_init leaf, every active CA entry must equal a recorded generation of its role (a role that the ca_init does not name is not compared). A conforming signer writes the ca_init leaf before its first bundle_install, so every real log gets the full rule and no existing fixture trips it. The closure of the switch has three links: 03-12b's chain rule (an entry changes only by add-next, by abort or, in 03-12e, by the switch, which makes a `next` entry active with its key unchanged), this plan's `next` rule (a `next` entry is logged before it can be switched), and this rule for every log that has a ca_init (once 03-12b lands, a successor that changes an active key is refused by the chain rule before this rule is reached, so the trigger that stays reachable here is a genesis bundle whose active keys differ from the ca_init's). 03-12e keeps the switch in the shared chain rule that VerifySuccessor runs, and pins that with `switch_activating_unlogged_key_refused`. This narrows an earlier draft's unconditional rule; the effect is the same for every log a conforming signer writes.
- *doctor shows generation and state, not trusted_until.* trust.CAEntry has no TrustedUntil at d15f044 (internal/trust/bundle.go:91-98), and an always-empty field would be dead surface. 03-12c adds the field and the display, and carries internal/doctor and cmd/keyroster-signer/doctor.go in its file list for it. doctor.Facts gains a list of generation facts (role, generation, fingerprint, alg, custody, state: `active`, or `prepared` when the bundle names no such entry) and leaves CAKeys alone, so custodyResults and the existing doctor tests are unchanged.
- *installed_issued_at_after_now is a WARN.* An installed bundle may legally be up to 300 s ahead at install time, and time passes; a lasting lead means the signer's clock moved back or the bundle predates the check. It blocks later successors (trust/verify.go:373-377), which the message says, but it is not a failure of the signer, and clock regression already has its own FAIL.
- *issued_at comparison.* issued_at is whole seconds; the signer clock has sub-second resolution. The install refuses when `issuedAt.After(now.Add(krl.PruneMargin * time.Second))` at full resolution: exactly 300 s ahead is accepted, one nanosecond more is refused. The tests use whole-second clocks for the 300 s and 301 s cases and one pair of sub-second cases at the boundary.
- *prepare presupposes an installed bundle.* The distinctness checks name roots, bundle keys and policy admins, which exist only once a bundle is in force. Without one, `ca-rotate prepare` refuses with ErrNoTrustBundle. A rotation has nothing to rotate before the first bundle.
- *The backend gate runs on the stored name before any backend is opened.* The registered backends are agent, software, tpm and piv (internal/keystore/*/: keystore.Register); `pkcs11-agent` is a custody label of the agent backend, not a backend. `signer.CheckRotationBackend(name)` accepts agent and software and refuses tpm and piv with `rotation_not_supported_on_backend`, naming 03-12f, so the refusal needs no device. 03-12f deletes two map entries.
- *Custody never changes in a rotation.* The new key's custody must equal the custody recorded for the role's generation 1 (`rotation_custody_mismatch`). backend_config holds one row (signerdb/migrations/0003_trust.sql), and moving a CA into another custody is a later plan.
- *Prepare with `--key` is generic.* A selected key is opened with KeyFor at the next generation number and an empty location, so the agent backend takes any loaded key and the software backend takes a file an operator placed as `<role>-g<N>.age`. Without `--key`, the backend must implement keystore.GenerationProvisioner (software), otherwise `ErrKeySelection` says to pass `--key`.
- *The output file is claimed after the state and the backend are open, and before anything is committed* (as ca-init does, cmd/keyroster-signer/cainit.go): an O_EXCL create of `--out`, removed again by every error path after the claim. A refusal of openState (the state lock, the restore marker, a bad state directory), of the backend gate by name or of the backend opening therefore leaves no `--out` file, and a retry is not blocked by one. If the commit succeeds and the final write fails, the error says the generation is recorded and names the file.
- *The prepare file is canonical JSON by trust.CanonicalJSON* with fields in the order role, generation, key, alg, custody, written by cmd/keyroster-signer/rotate.go. 03-12b's reader is written against these bytes, which a golden test pins here (`prepare_file_bytes_pinned`).
- *ca_generation bodies refuse generation below 2.* Generation 1 is ca_init's. The decoder is strict and canonical (round trip, no trailing byte); the chain rule (previous plus 1) is enforced by the signer's cross-check and by audit.
- *The cross-check lives in the log walk.* `loggedGenerations` is fed by ca_init and ca_generation leaves in rebuildLogFrom and in CheckTrust's own walk (logstate.go:283-297), and compared with LogSnapshot.CAGenerations, read in the same transaction as the leaves (signerdb/log.go ReadLogWithHashes). Serve (initLog), install-bundle, ca-rotate prepare (newLogWriter), recover-revocations and doctor (CheckLog and CheckTrust) all pass through it.
- *No edit to status.go, commands.go, serve.go, cainit.go or install.go.* Status reports `trustState.caKeys`, which loadTrust now builds from the active generation per role and assigns only there (TestStatusWriters' one allowance stays exact); `ca-rotate` registers itself from an init function; the lock gate sits inside lockStateDir. An earlier draft listed status.go and commands.go; neither needs a change.
- *Recovery's marker release needs a seam.* A real recovery needs a signed request over a restored log (internal/signer/recovery_test.go builds one with the signer fixtures, which are not importable from cmd). cmd/keyroster-signer/recover.go calls the signer through `applyRecovery`, a package variable that tests replace (as cmd/keyroster/audit.go has `auditClock`); a refusal test uses the real signer.
- *RED route.* Task 1's R1 holds one test file and declares nothing (it refers to kind 14 as `tlog.Kind(14)`), so it builds on origin/main and fails at run time. Task 2 and Task 3 commit their tests first with only the declarations they need to build; tests that pin behaviour T1 already has pass on their R commit and are recorded as controls.
- *Pointer edits.* Every pointer duty of the set except one goes into this PR: 03-13 (seven duties, twelve insertions on eight lines), 03-15 (two) and 03-16 (two). The exception is 03-15's `--ca-next-fingerprint` pointer (its v4 command, rehearsal and the T-03-261 row), which the owner placed with 03-12b, the plan that adds the flag.
- *prepare compares a new key with every root the log records, and the admin rule is narrower on both sides on purpose.* PrepareGeneration compares the key with the root keys of every bundle the log records (`loaded.roots` of the writer's log walk, which loggedInstalls.checkAdmins already uses), retired roots included, because audit refuses a ca_generation whose key equals a root of any accepted bundle (`a.roots`): a leaf that the signer wrote and audit refuses would make every later export of the installation fail, `keyroster revoke recover` included, and the log is append-only. Admins are compared with the policy in force on both sides (the signer: the installed policy; audit: the policy in force at the leaf). The earlier draft of this plan, reviewed with the owner, refused "an admin key seen so far"; this plan narrows that on both sides together so that the signer and audit agree, because the wider rule needs the admins of every policy on both sides and widening only one side would recreate the split described above. A key that was an admin and has since been removed can therefore be recorded as a CA generation. This is a deviation, listed in the ledger for the owner to confirm in review; the wider rule adds `key_equal_former_admin_refused` to TestPrepareGeneration and TestVerifyCAGeneration.
- *A software key is provisioned last.* PrepareGeneration opens the log key, builds the writer (the log checks, `generations_not_logged` included, run there) and reads every distinctness input before it provisions, so that only a failure of the final commit, or a collision of a freshly generated key, can leave a `<role>-g<N>.age` file that no row records; the error then names the file. A restore can leave one too, because the row and the leaf are gone and the file is not: doctor warns `unrecorded_generation_file`, in words that give the conditions (a prepare may be running, or an operator may have placed the file for a `--key` prepare), and the runbook says that after a restore such a file is a lost prepare's key, to be destroyed and never recorded again with `--key`, unless the operator placed it for a `--key` prepare.
- *The release is also written to the journal.* The signer's own commands log through slog to stderr, which reaches the journal only under a systemd unit, and the release commands are run by an operator in a terminal. So `releaseRestoreMarker` and `--no-recovery-needed` also send the same text as one datagram to the native journal socket (`/run/systemd/journal/socket`; PRIORITY=4, SYSLOG_IDENTIFIER=keyroster-signer, MESSAGE=the text), best effort: an absent socket is not an error and changes no exit status. The path is a package variable, so a test listens on its own socket. The identifier is set by the sender and any local user can write to that socket, so the entry is a record and not proof: the runbook filters on journald's own `_UID`. cmd/keyroster-signer already holds the network capability (test/capslock/keyroster-signer.json), so no new capslock pair is expected; `scripts/capslock-check.sh` decides.

## The output contract

These texts and names are fixed, byte for byte where tests match them.
- **ca-rotate prepare** (cmd/keyroster-signer/rotate.go): `keyroster-signer ca-rotate prepare --state-dir D --role user|host|machine [--key SHA256:...] [--backend-opt k=v] --out FILE`. On success it prints one line `role <role> generation <N> <fingerprint> <alg> <custody>` and `prepare file: <FILE>` on stdout. FILE is canonical JSON with a trailing newline, mode 0644, created with O_EXCL: `{"role":"user","generation":2,"key":"<authorized_keys line>","alg":"ssh-ed25519","custody":"software"}`.
- **The refusals** are command errors (the signer's local commands never classify, so classify and the format registry's refusal-detail section are untouched). Each message contains its name: `rotation_role_not_supported` (ops and log: 03-13), `rotation_not_supported_on_backend` (tpm, piv: 03-12f), `rotation_custody_mismatch`, `generations_not_logged`, `bundle_issued_in_future`, `restore_recovery_pending`. prepare's key refusals reuse ErrKeySelection and ErrBundleKeys with these reasons: the key equals a stored generation, a root key of any bundle the log records (a rotated-out root included), a key of the installed bundle in any state, or an admin of the installed policy.
- **The marker.** The file name is `restore-recovery-pending`. `restore_recovery_pending` is refused with the text `<dir>/restore-recovery-pending exists: this state directory was restored and no recovery has been applied or ruled out; run keyroster-signer recover-revocations (docs/runbooks/signer-install.md, restore step 2b)`.
- **Release lines.** After a successful recovery, recover-revocations prints its existing `recovered: ...` line on stdout and `restore-recovery-pending removed: <path>` on stderr, and sends the same text, as one entry, to the journal. `--no-recovery-needed` prints `restore-recovery-pending removed: <path>` on stderr and in the journal, or `no restore-recovery-pending marker in <dir>` and exits 0 when there is none; it reads no standard input and opens no database, and a marker that os.Remove cannot remove (a non-empty directory) is refused with `remove <path> by hand`. The journal entry is one datagram to `/run/systemd/journal/socket` (PRIORITY=4, SYSLOG_IDENTIFIER=keyroster-signer, MESSAGE=the text), best effort: no socket is no error.
- **`--migrate-only`.** `keyroster-signer recover-revocations --state-dir D --migrate-only` reads no standard input, takes the exempt lock, requires `signer.db` to be an existing regular file (a missing file, a symlink or a directory is refused, with doctor's text; it never creates one), opens it with signerdb.Open, which applies a pending migration, and prints `migrate-only: signer.db is at the schema this binary reads; restore-recovery-pending kept: <path>` on stdout, or `migrate-only: signer.db is at the schema this binary reads; no restore-recovery-pending marker in <dir>`. It writes nothing else, never removes the marker, writes no journal entry, and excludes `--no-recovery-needed` (usage error `--migrate-only and --no-recovery-needed exclude each other`).
- **doctor.** `FAIL restore_recovery_pending`, `WARN installed_issued_at_after_now`, `WARN unrecorded_generation_file` (a `<role>-g<N>.age` file in `{state-dir}/software` that no generation row names; the warning says that, if no prepare is running and a restore came before it, it is a key from a lost prepare, to be destroyed unless the operator placed it for a `--key` prepare), and one `OK generations` line when the database holds any generation fact, naming each role's active and prepared generations with their fingerprints.
- **audit verify.** `CA generations: N` after the probe line and before `anchored:`, printed only when N is above 0.
- **Files.** software generation files are `<role>.age` for generation 1 and `<role>-g<N>.age` from 2, mode 0600 in the 0700 `{state-dir}/software` directory.
