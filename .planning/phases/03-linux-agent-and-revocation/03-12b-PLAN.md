<objective>
An admin can add a prepared CA key as `next` through one root ceremony, so every host trusts it beside the active key, and can withdraw it again by an abort. The chain rule that makes this safe, the ceremony tool and its summaries, the agents' answer checks, the runbook and an end-to-end test against real sshd all ship together.

Purpose:
- **The rule.** 03-12 recorded generations and kept checkBundleKeys from accepting any CA entry that d15f044 refused, so a root-signed successor still cannot change a CA entry. Here it may change one in exactly two ways, and the rule that says so is shared by the signer, every agent, audit and the ceremony tool, so a bundle the ceremony builds is a bundle all of them accept, and no other CA change is accepted anywhere.
- **The withdrawal.** An abort is a narrowing change on every host and takes the key out of the agent's answer checks in the same plan, so a `next` key that turns out wrong or compromised is not left trusted anywhere that decides who may answer.
- **The root holders' view.** A root signature vouches for the bundle, so the ceremony prints what changes in the CA entries and in the root set, and refuses a `next` key whose fingerprint the second person did not read from the signer console.

## Planner decisions (Claude's discretion), recorded with their reasons

- **The chain rule matches entries by generation, per role.** `checkCATransitions(prev, next *Bundle) error` compares the entries of each of user, host and machine by generation number (Validate already orders them by role and increasing generation and forbids duplicate generations), so the order in which a bundle lists them cannot hide a change. 03-12e adds the policy arguments when its rule needs them; here they would be unused parameters.
- **Added keys are distinct from each other as well as from the previous bundle.** The design says a new key equals no key of the previous bundle and leaves duplicates within the successor to Validate. Two roles adding the same new key in one successor would pass the per-role rule and fail Validate, which production runs first, but FuzzCATransitions states that an accepted pair Validates, and the rule should hold that on its own. The extra check is one set lookup. "Keys of the previous bundle" means every CA entry in any state, the ops key, the log key and every root key.
- **The rule is called after the checks that need no CA knowledge.** In checkSuccessorChain, after the policy parse, the version, prev, issued_at, policy-hash, installation-ID, policy-chain and carried-custody checks and before CheckAdminsNotRoots, so a successor that is wrong in two ways reports the older, more basic refusal, and the ceremony clock hint of `errIssuedBeforePrev` is unchanged.
- **`SuccessorOptions` is the signature, not a wrapper.** `BuildSuccessor(prev, prevCanonical, prevPolicy, o SuccessorOptions)` with Roots, Threshold, Policy, IssuedAt, InstallationID, CANext and CARetire. The early plan fixed this so that 03-13 and 03-14 add fields instead of re-cutting the signature. A wrapper that kept the old signature would leave 20 test call sites alone, but it would keep the signature that the owner-reviewed scope replaces, and the mechanical sweep is one behaviour-neutral commit (S0 in Task 1) that reviews in minutes.
- **The agent tests are rebuilt on chain-legal bundles before the rule exists (commit P1, tests only).** A throwaway prototype of the rule, run on a scratch copy of a624b04 against the unchanged tests, failed exactly these (the rest of internal/agent, internal/server, cmd/keyroster, cmd/keyroster-signer and internal/doctor stayed green): in internal/agent/apply, TestKRLSigner (`retired_key_krl_after_a_poll_from_the_record_is_refused`, `retired_key_krl_during_a_wait_from_the_record_is_refused` with its `poll` and `forward` legs, `retired_key_krl_during_a_wait_above_the_record_is_refused` with its two legs, `record_signed_krl_during_a_wait_lands` with its two legs), TestSpoolWindowWideningWait (`remade_chain_under_the_old_policy`, `newer_directory_under_the_policy_in_force`, `fork_at_the_record_version`, `record_version_withheld`, `remade_chain`, `nothing_new`, `older_bundle_at_the_window_boundary`) and TestSpoolWindow/`bundle_ca_line_window_newest_then_fixed_bundle_applies`; in internal/audit, TestVerifyAnchoring/`successor_ca_rotation_checked`; in internal/signer, TestSuccessorForeignCAKeyRefused (its three roles). ## The output contract

These texts and names are fixed, byte for byte where tests match them.
- **The CA-change section** (`rootceremony.CAChanges(prev, next *trust.Bundle) string`). When no CA entry differs: the one line `CA entries: unchanged`. Otherwise one line per differing entry, in the bundle's order (role, then generation), each `CA <role> gen <N> <fingerprint>: <old> -> <new>`, where `<fingerprint>` is the SHA256 fingerprint of the entry's key, `<old>` is the state in the previous bundle or the word `none` for an added entry, and `<new>` is the state in the successor; an entry the successor lacks (the chain rule refuses it, so only a direct call prints it) is `... <old> -> removed`. Example: `CA user gen 2 SHA256:abc...: none -> next`, and for an abort `CA user gen 2 SHA256:abc...: next -> retired`. No line begins with `  webauthn`, `  pop`, `  timelock `, `installation id: `, `Policy in force:`, `Trust bundle version` or `signed by `.
- **The root-set line** (`rootceremony.RootSetLine(prev, next *trust.Bundle) string`): `Root set: unchanged` when the two root key sets are equal (by wire encoding, in any order), else `Root set: CHANGED (added N, removed M)`.
- **Placement.** `root sign --prev` prints the section, then the root-set line, right after `successorHeader` (root.go:549) and before Summary (:554); the threshold-1 warning goes to stderr and is unaffected. `trust verify --prev` prints them right after its `Successor of trust bundle v<N>, sha256 <hash>` line (trust.go:185) and before Summary (:186). Genesis outputs print neither.
- **Flags** (`keyroster root sign`, each repeatable): `--ca-next ROLE=FILE` (ROLE is user, host or machine; FILE is 03-12's prepare file), `--ca-next-fingerprint ROLE=SHA256:...` (required for every `--ca-next` role and refused for any other role), `--ca-retire ROLE:GEN` (GEN is a canonical decimal generation number; the entry must be a `next` entry of the bundle in force). All three need `--prev` and are usage errors (exit 2) without it; at most one change per role across the three flags is a usage error; a fingerprint that is not the file key's is exit 1 with `ca_next_fingerprint_mismatch` in the message, before anything is written or signed; `--installation-id new` combines with them. Every root that co-signs the successor passes the same flags, because prepareBundle rebuilds the bundle from them and refuses a different one.
- **The refusal of `--ca-pubkeys` with `--prev`** (exit 2): `root sign: --ca-pubkeys is for a genesis bundle; a successor changes CA entries only with --ca-next and --ca-retire`.
- **The usage errors of the three flags** (exit 2, each printed on stderr after `root sign: `; the angle-bracket words stand for the values given). Without these texts an unknown-flag error, which also exits 2, would pass for any of them before the flags exist, so each case asserts the exit code and its text:
  - `--ca-next, --ca-next-fingerprint and --ca-retire need --prev`;
  - `--ca-next <role> needs --ca-next-fingerprint <role>=SHA256:...`;
  - `--ca-next-fingerprint <role> needs --ca-next <role>=FILE`;
  - `at most one CA change per role: <role> is named more than once` (across the three flags, a repeated flag included);
  - `<flag> <value>: the role is not one of user, host and machine`;
  - `--ca-retire <value>: want ROLE:GEN with GEN a decimal generation number from 1 to 4294967295`;
  - `--ca-next <role>=<file>: the file holds role <file role>, not <role>` (the flag's role must be the role inside the prepare file, so a key prepared for one role cannot be added under another by a slip of the flag).
- **The prepare file** is read strictly: `trust.DecodeStrict` into the struct of cmd/keyroster-signer/rotate.go:122 (role, generation, key, alg, custody, in that order), at most 4096 bytes, role one of user, host, machine, generation at least 2, key in the canonical form `trust.FormatKey` prints and equal to `alg` in type, custody non-empty. The exact bytes that rotate_test.go:529 pins parse to role `user`, generation 2, that key, algorithm `ssh-ed25519` and custody `software`.
- **Chain-rule refusals** are ErrVersionChain with the text `CA <role> generation <N>: <reason>`, the reasons being `an entry is removed`, `an entry changes (only a next entry may become retired)`, `a new entry must be next`, `the role already has a next entry`, `the generation is not above every earlier generation of the role`, `the key equals a key of the previous bundle`, `the key is added twice in this successor` and `more than one change for this role`.
- **The signer's refusals** are ErrBundleKeys with `CA <role> is next but generation <N> is no stored generation of that key`, the same with `retired`, and `CA <role> is draining; the switch arrives in 03-12e`.

## Lessons from 03-12's pre-merge review, and where this plan applies them

- Every `grep -x` over text with brackets or other regex metacharacters is `grep -Fqx` (03-12's publish gate failed with "Invalid range end"): Task 1's stop guard and every gate here use `-F`.
- A verify command that scans added lines scans only added lines: every such scan reads `git diff -U0` and keeps `+` lines without the `+++` headers, and the golden check reads the removed lines of `-U0` output; no scan reads context that is already on main.
- The executor runs `git diff --cached` on every staged file and reads all of it before each commit: the Delivery protocol says so as an explicit step, every task's acceptance criteria repeat it, and the SUMMARY records it per commit.
- A root-run shell in a runbook that writes into a directory owned by a less-privileged account does not follow links: ca-rotation.md moves files in and out of the signer's directory as the signer's user and root runs nothing below `incoming/`, not even `rm -f` (the restore block's `rm -f` is safe only because it removes direct children of the state directory), and TestCARotationRunbookLinkSafety pins it as an allowlist over joined command lines (the restore block of signer-install.md and `restoreSignerPathWrite` in test/e2e/restore_test.go are the model for the hazard; the denylist form was judged too weak for a runbook that wraps commands over several lines).
- A capslock pair that changes is listed and explained: the prediction is none, with the reason, and the executor records the counts after T1 and T2b and explains any pair before `--update`.
- The new CI job is pinned by SHA like the others (`check-pinned-actions`), and is added to the ruleset file and CONTRIBUTING.md, in the order CONTRIBUTING.md:222-226 requires.
