**Signer.** Revoke dispatches on Target:
- key_id: one key_id entry and row per CA key of the role in the bundle in force (two during a 03-12 rotation, one otherwise), in the CA keys' wire-byte order, so signer and audit expect the same set; each entry's ValidBeforeSeconds is the ValidBefore of the issuance row with that key ID under that CA key when present (prunable), else 0 in the leaf and NULL in the row: unknown, never pruned (krl.Prunable below).

- subject user: `signerdb.LiveIssuanceForSubjectTx(ctx, tx, "user", name, at)` with at = the revoke's ResolvedAtSeconds (T) selects issuance rows with ca_role user whose key_id starts with `kr1/ca=user/sub=<name>/` or `kr2/ca=user/sub=<name>/` (an exact prefix compare with `substr(key_id, 1, length(?)) = ?`, never LIKE, in which `_` matches any character), confirms the subject with cert.ParseKeyID, parses the stored certificate and returns those with `krl.EntryLive(ValidBefore, T)`; each becomes a serial row. **No exclusion of certificates already revoked (PR #60 review, Codex docs review, medium).** The resolver does not consult the revocation table: a live certificate that an earlier revoke (a serial revoke, a first sweep, a previous `revoke user`) already recorded is returned again and gets another serial row and leaf entry. Why: audit re-derives the resolved set from the issue and login_issue leaves and T alone, with no history to track; excluding "already revoked" would need a rule for which earlier entries count (serial rows only, or key-ID and explicit-key entries that also refuse the certificate; under which CA key; a row pruned by then), and every such rule is a place where signer and audit can diverge in the fail-open direction. Re-listing is a superset, so it is fail-safe, and it makes a re-run of `revoke user` idempotent, which the exit 3 and 4 guidance assumes. 03-01 already allows a serial to be revoked twice (one row per revoke). The duplicate rows are harmless: krl.Encode merges sections with the same CA key wire bytes and lists a serial once (03-01, internal/krl/krl.go Encode and split), the extended encoder keeps that for key IDs and explicit keys (below), and pruning is per row, so an entry stays while any of its rows is not krl.Prunable. There is no issued_at cutoff: certprofile.ForRole reads the TTL cap from the policy, so a cutoff of "now minus the current max TTL" would miss a certificate issued under an earlier policy with a longer cap (addresses review concern: Codex 03-03 HIGH, issue-time cutoff mixed with ValidBefore, REVIEWS L93@e7b3b32, and Consensus Agreed Concern 10, L1334@e7b3b32). An empty result still records the revoke (the leaf lists zero entries, the request ID goes into revoke_request) and publishes, so the log shows the action. A subject that resolves to more than tlog.MaxRevokedEntries (4096, internal/tlog/leaf.go:100) certificates is recorded as consecutive revoke leaves of the same request in the same transaction, entries in ascending serial order, every leaf but the last carrying exactly 4096 entries, followed by one publish; the revoke_request row is written once, so a replay is still refused `duplicate_request`. Revocation must never fail on size (03-03 plan check; a per-subject issuance cap was the alternative, not taken).
Every target records the request ID and appends one revoke leaf whose Entries list the resolved rows (several only for a subject above 4096 entries). publishKRLLocked builds the set from all revocation rows, never filtering by the CA keys the bundle in force trusts, leaving out serial and key-ID rows for which `krl.Prunable(valid_before_us / 10^6, issued_at)` is true. It does so through `krl.PublishSet(entries []krl.Entry, issuedAt uint64) (krl.Set, error)`, the one set builder that signer and audit both call (PR #60 review): a krl.Entry is one revocation row (signer) or one logged revoke-leaf entry (audit) with its kind, CA key, serial, key ID, key and ValidBefore (0 when unknown); PublishSet leaves out each entry for which krl.Prunable is true at issuedAt and puts the rest into the Set as they are, duplicates included, so an entry revoked twice stays while either copy is live, and krl.Encode merges and dedupes (`TestPublishSetDuplicates` in Task 2).

**Resolution time and the clock clamp (F9; addresses review concern F9, REVIEWS L1369@e7b3b32, L1435-1441@e7b3b32).** internal/krl/krl.go adds `const PruneMargin = 300` and `func EntryLive(validBefore, at uint64) bool` (validBefore + PruneMargin > at, whole seconds; saturating so validBefore near 2^64 stays live), the only liveness rule; signer subject resolution, publishKRLLocked and audit verify all call it, and nothing compares ValidBefore with a clock elsewhere. `func Prunable(validBefore, at uint64) bool { return validBefore != 0 && !EntryLive(validBefore, at) }` is the only pruning rule: 0 means unknown (NULL in a row, 0 in a leaf's ValidBeforeSeconds, as tlog.RevokedEntry documents), and an unknown entry is never pruned; read literally, EntryLive(0, at) is false, so without it a `revoke key-id` with no issuance row would leave the KRL at its own publish (03-03 plan check). publishKRLLocked and verifyKRLPublish prune with Prunable, both through krl.PublishSet; subject resolution uses EntryLive, because a stored certificate's ValidBefore is always known. A ValidBefore that does not fit the row's microseconds (validBeforeMicros returns 0 at 2^62 µs and above, as for ssh.CertTimeInfinity) is stored as NULL and never pruned, while the leaf keeps the certificate's value, for which EntryLive stays true at every realistic time, so signer and audit agree. T and issued_at are the 03-01 values: the call's single clock reading truncated to whole seconds, recorded in RevokeBody.ResolvedAtSeconds, KRLPublishBody.IssuedAtSeconds and the manifest. Truncating before comparing keeps signer and audit equal at sub-second boundaries: for an integer boundary E, "E ≤ now" holds exactly when "E ≤ floor(now)". appendLocked's clamp may raise a leaf's TimeMicros above the reading after a clock step back; audit therefore never evaluates liveness at a leaf's TimeMicros. After a step back the reading is earlier than the true time, which can only make more certificates live, so revocation keeps working (issuance refuses `clock_regression`; revoke does not).

**No live entry is dropped (shared contract with 03-05's two-step swap).** Because the KRL is built from every row and only EntryLive removes serial and key-ID entries, the entries of version n+1 differ from version n only by new revocations and by entries not live at n+1's issued_at. 03-05 relies on this for KRL_M = KRL_B. The contract holds while the rows are intact: a signer restore replaces the rows themselves and can lose revocations, which is T-03-207 and Task 3's stop, not a publish path (03-05's swap assumes intact rows; the restore-recovery plan owns the restore). A clock that steps back can make a pruned entry reappear (harmless); a signer clock more than 300 s ahead of the hosts' clocks prunes early, the same assumption certificate validity already makes (threat T-03-205).
