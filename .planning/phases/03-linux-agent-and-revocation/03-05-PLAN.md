<objective>
Build the agent's apply engine, the place where lockouts happen, and prove it offline against real sshd before any network code exists. Signed state comes in and is verified against the agent's own pins. It is rendered into a generation and checked with the host's own `ssh-keygen` and `sshd -t`. Then it is swapped in, through an intermediate generation when a change both adds and removes (F1), reloaded only when needed, self-tested, and rolled back on failure.

Purpose: AGENT-04 (atomic write, sshd -t, reload, self-test, rollback), AUTHZ-02 (principals files from the signed directory, through the one renderer), REVOKE-03 (atomic install, last-good, rollback refused, no lockout from a bad KRL). The sshd re-read behaviour the whole design rests on is pinned by a test on both CI OpenSSH versions.

Output: packages internal/agent/{state,spool,apply,paths}, the `keyroster-agent` binary (applier only; the fetcher is 03-07), two e2e tests, the dependency firewall generalised per binary, a capslock baseline, and a PR.

**Owner decision before implementation: D-05 against D-06 (Task 1).** D-05 gives the root applier no network access; D-06 requires a self-test that talks SSH to the host's own sshd after every apply. Taken literally they collide: the research's unit for the applier (`PrivateNetwork=yes`) leaves it a namespace with only its own loopback, from which the host's sshd cannot be reached. The first draft of this plan settled that as Claude's discretion; because it reinterprets a locked decision and shifts the threat model, the owner decides it in Task 1, before any applier code exists, and 03-06, 03-07, 03-08, 03-09 and 03-10 check the recorded answer instead of presuming it. Tasks 2-4 are written for the recommended answer, `loopback-only`: "no network access" then means no route off the host and no HTTP, TLS or RPC code; the unit (03-08) sets `IPAddressDeny=any` and `IPAddressAllow=localhost`; the code dials only loopback addresses, and only for the sshd self-test (and the 03-10 probes); a host whose sshd listens on no loopback-reachable address is refused with an explanation (03-06 adds that check to the D-07 refusals). Whether any dogfood host's sshd listens only on a tailnet address is not recorded (the 02-14 SUMMARY and host-setup.md contain no ListenAddress); 03-16's preflight shows it.

**Spool format (Claude's discretion: the fetcher/applier IPC).** A directory of files written atomically by the fetcher (03-07) and read by the applier: `bundle-<v>.json`, `bundle-<v>.json.sigs`, `policy-<v>.json`, `policy-<v>.json.sigs`, `directory-<v>.json`, `directory-<v>.json.sigs`, `krl-<v>.krl`, `krl-<v>.manifest.json`, `krl-<v>.manifest.sig`. Each kind has a size cap, and unknown names are ignored and reported. The spool holds data only, never commands: the applier treats every byte as untrusted and re-verifies it. The applier reads the spool only through the descriptor-relative, no-follow, non-blocking open contract of spool.ReadFileAt (F2, REVIEWS L1362@e7b3b32).

**Two-step swap (F1, owner decision 2026-10-24, REVIEWS L1460@e7b3b32).**
- **The problem.** sshd checks the KRL, then the CA file, then the principals file, each through its own open. A single `current` swap between those reads can show one authentication a mix that accepts a certificate neither generation accepts (REVIEWS L1395@e7b3b32). The research's "one swap, one consistent state" (03-RESEARCH "Atomic apply", Layout) is therefore superseded.
- **The fix.** The owner chose the two-step swap with no reload, over immutable `gen/N` paths with a reload per apply and over accepting the window. Apply moves A → M → B, where M is an intermediate generation that allows only what both A and B allow. It waits longer than LoginGraceTime between the two swaps. When M equals A or B, it swaps once.
- **Reuse.** 03-12 (CA rotation) and 03-14 (break-glass files) install new trust content through `apply.Apply` and must not add a direct swap of their own. 03-09's host trust is client-side and is not affected.
</objective>

**Flagged assumption, AGENT-04 two-step swap (F1, owner decision 2026-10-24).** The two-step swap is safe under three premises:
1. sshd reads the KRL (for the key and its signing CA key), then the CA file, then the principals file for each authentication. This was verified against 9.5p1 and 10.5p1 source in the Verification Round (REVIEWS L1397@e7b3b32). TestSwapInterleaving models the order but does not observe it in a running sshd.
2. No pre-authentication read outlives LoginGraceTime. This is stated in sshd_config(5), and `login_grace_closes_preauth` observes the disconnect on both CI versions. The wait uses an upper bound: the largest value observed since the agent's own last reload, kept in `login_grace.json`. Residual: a value raised and reverted again by hand, with reloads, between two observations is not seen. The observations are at start, at every apply and at every drift check (15 min). The owner accepted this residual on 2026-10-24 (REVIEWS L1496@17b9de6), because host root is already trusted with its own sshd in the threat model. Pinning LoginGraceTime in the drop-in, and tracking pre-auth children through /proc, were both rejected. ObserveLoginGrace stays the mechanism (T-03-232).

**Residual, owner-accepted 2026-10-24 (checker iteration 3; REVIEWS "Owner decision on the manual-recovery residual", L1499; T-03-233): a foreign `current`.** While something other than the agent has pointed `current` at a readable foreign X, sshd enforces X's own content until the operator runs `--recover-to-last-good`. During that run's window (narrowing swap at once, widening swap after the LoginGraceTime bound), a mix of reads is accepted only if X or last-good accepts it, never only if last-good does. Recovery adds no permission of its own. The exposure is whatever X granted, and X was installed by host root or something acting as root, which the threat model already trusts with its own sshd. A dangling X, or one without revoked.krl, has no such window.
3. KRL entries leave only through 03-03's pruning: `krl.EntryLive`, every KRL built from all revocation rows, and `TestPublishNeverDropsLiveEntry`. The rule's 300 s margin is measured on the signer's clock. A host clock more than 300 s behind it can see a pruned certificate as unexpired during the first swap. Explicit-key entries are guarded by `krl_drops_key_entry`.

Additions wait up to LoginGraceTime + 30 s (150 s by default; owner decision 2026-10-26, PR #67) after the previous swap of `current`: always within a two-step apply, and for an add-only apply when another swap happened in that interval. Revocations and removals never wait. The operator runbook gets the rule in 03-07, and 03-16 measures it.

**Clock precondition (owner decision 2026-10-24, REVIEWS L1486@af84cd5).** KRL_M = KRL_B also assumes the host clock is within 300 s of the signer's. The owner kept KRL_M = KRL_B: a host lagging by more than that already accepts expired certificates in steady state, so the root cause is clock health, and a union KRL would put the encoder in the root applier. 03-08's `clock_skew` alert (|clock_offset_s| > 300, whole-second resolution, measured against keyroster-server's clock as the closest stand-in for the signer's) monitors the precondition.
