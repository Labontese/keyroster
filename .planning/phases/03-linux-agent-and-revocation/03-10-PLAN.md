<objective>
The signer issues, logs and revokes probe certificates by proof of possession, audit re-proves them, and real sshd is shown to accept the positive certificate and refuse the negative one as the host agent's self-test (03-10b) needs.
- A host agent's request (frame 0x0B) carries an ephemeral probe key and two proofs of possession. The signer issues a restricted machine-CA certificate that sshd accepts only for the probe account of that host, from loopback, with no session.
- The negative certificate is revoked by its own serial in the same transaction. The KRL lists it until it expires, the explicit-key cap is untouched, and a renewal rides the hourly republish unless the host would be left without a published negative.

## Planner decisions (Claude's discretion), recorded with their reasons

- **Five tasks, no merge-gate task.** The owner's merge (01-SKELETON steps 5 to 7) follows Task 5, which ends at a green, reviewed PR; `autonomous: false` records the wait and Task 5's last paragraph carries the resume signal. No task merges or enables auto-merge.
- **The probe job lives in e2e.yml.** GitHub's documentation says a `workflow_dispatch` workflow must exist on the default branch; whether a file that exists only on a branch can be dispatched was not tested, and this plan does not rely on it (a new workflow file might be neither gated nor run RED before the merge). A new job in the existing file is dispatched like the existing lanes (03-09b dispatched e2e.yml on a throwaway branch the same way), shares the pinned actions and the OpenSSH cache key, and its jobs are read one by one (`gh run view --json jobs`, then `--job ID --log`).
- **A build tag keeps the probe tests out of the main lanes.** The two tests carry `//go:build e2e && e2eprobe`, as agent_systemd_test.go carries `e2e && systemdsmoke`. The main lanes (`-tags e2e`) then compile neither test, and the job runs `-tags "e2e e2eprobe" -run '^(TestProbeCertsAgainstSSHD|TestProbeSSHDFacts)$'`. A `-skip` pattern would edit the main lanes' command. The "lanes did not grow" gate is deterministic: no `=== RUN   TestProbe` line in either main lane's log (lane times swing 745 to 801 s in 03-09b, so a timing gate would not be one).
- **The reservation sits at the signing funnel.** The design lists admin issue, login and 03-11's machine issue as separate refusal sites. Every certificate is signed through cert.Build and re-checked by audit through cert.CheckIssued, so a `cert.Profile` flag that only ProbeProfile sets covers every path on main (and 03-11's from 03-11 on, held by the guard test below), and audit gets the rule for free. The helper lives in internal/cert/builder.go rather than a new directory function, and the install-time refusal is in InstallDirectory. The CLI edit path, which the design also names, is not changed (P3): the CLI has no local principal rule, so a refused install prints the signer's `principal_reserved` or `account_reserved`. One rule at one place.
- **The probe index is its own file** (probeindex.go, like hostindex.go) and is staged in a pending copy and installed after COMMIT, as pendingHosts is.
- **The prompt flag is derived.** The signer keeps one bool, "an early publish is wanted", and the time of the last probe-caused publish, under s.mu. republishIfDue honours the flag only while the index still holds an unpublished negative certificate and the last probe-caused publish is at least one krlCheckInterval old, so any publish by anyone clears its cause, the flag needs no clearing in the other publishers, and two probe-caused KRL versions are never closer than a minute (plan check 1: a flag branch without the age gate let a flagged tick follow an immediate publish within seconds, so "one a minute" did not hold). A restart loses the flag; the row then rides the hourly publish (up to one hour), which is the rule's own fallback.
- **The window is computed from the new lifetime.** `probe_cert_recent` uses L, the lifetime the new certificate gets (min(604800, cap in force)), recorded as the leaf's CapSeconds, so a lagging previous certificate never strands a host (the Q-09-2 reasoning). The rule is one function, `certprofile.ProbeCertRecent`, called by the signer with its clock and by audit with the new certificate's ValidAfter + 300, as 03-09 did for hosts, and `certprofile.ProbeLifetime` is the one place that turns the machine cap into L; audit judges the window with the leaf's CapSeconds. Revoking the latest probe certificate does not shorten the window: a replacement waits at most one window (residual).
- **One size rule for every row.** publishKRLLocked is the only place on main that checks the KRL size (krl.go:62-68), and a riding or flagged Negative row never reaches it. krl.go therefore gets `buildKRLLocked` (everything publishKRLLocked does up to and including krl.Encode, with the `krl_too_large` mapping), which publishKRLLocked calls and `checkKRLFitsLocked` calls and discards. Every Negative issuance runs one of the two inside its own transaction after the row insert, so a refusal rolls back the row, the leaf and the serial together. The invariant kept is weaker than the old comment's "never holds an entry no published KRL carries" (a riding row already waits up to an hour for the next publish): every transaction that writes a revocation row encodes the whole publish set, so the committed row set always encodes within krl.MaxKRL at the commit's clock, and the next publish carries it because expiry only shrinks the set. A gate keeps `krl.Encode(` single in the signer's non-test code.
- **Audit tests are modelled on `hostFixture`.** A `probeFixture` with a `wantFail(t, want)` that requires an error containing a message that names the broken rule, as `hostFixture.wantFail` does (verify_test.go:3886), so each fail-direction case isolates one rule and a check-free verifier stub fails all of them. The cross-host form is used for the entry-lists-the-key rule in the signer and in audit: host B's name with host A's listed key and a valid host-pop by A's key.
- **One guard for the reserved flag.** A guard test in builder_test.go, in the style of TestSignCertOnlyInBuild (signcert_guard_test.go:101) and reusing its token matcher, fails the build if any non-test file other than builder.go and certprofile.go names `ReservedPrincipals`, or any file other than certprofile.go and the two probeissue.go files names `ProbeProfile`. The claim that 03-11's machine issue is covered rests on it from 03-11 on.
- **Evidence order is fixed** (host-pop/v1, then probe-pop/v1), so the leaf is deterministic and audit checks index by index.
- **Plan totals.** The plan totals in ROADMAP (`N/M plans executed`) and STATE follow the files on disk, as in 03-09 and 03-09b: this plan owns only the wave count. M becomes 31 when 03-10b's plan file lands and 32 with 03-10c's. This differs from the design note's "23/32" and is recorded as a deviation.
- **Local gates first, CI at the end.** Tasks 1 to 3 gate on WSL (`scripts/linux.sh`) with both OpenSSH builds; the CI job is added in Task 4, run RED once on a throwaway branch and GREEN on the work branch, and its first PR run is Task 5's.
- **Restore drill.** The restore drill in the main e2e lane is not extended (Q6: the main lanes do not grow). The lost-negative-probe path is covered by unit tests (audit lookup, signer log) and stays UNVERIFIED end to end (residual R9).
- **Test-time rule (Q-09-3, with 03-09b's lesson).** One fixed package list serves the base and every delta reading: `./internal/signer/ ./internal/audit/ ./internal/server/ ./internal/cert/ ./internal/tlog/ ./internal/wire/`. The whole-module `./...` run is pass or fail only and is never compared with the base.

- **The publish rule.** In a Negative issuance's transaction, after `InsertRevocation`, with `pred` the host's latest negative certificate before this issuance, exactly one of three things happens. (1) `pred` is published and valid until at least now + 2 h (`probePublishMargin`): the row rides the hourly republish, and the transaction runs `checkKRLFitsLocked`. (2) Otherwise, the last probe-caused publish is younger than `krlCheckInterval` (a clock that went back counts as old enough): the row is written with no publish, the transaction runs `checkKRLFitsLocked`, and after COMMIT `probePrompt` is set. (3) Otherwise `publishKRLLocked` runs in the same transaction, which applies the same size rule through `buildKRLLocked`. A `krl_too_large` from (1), (2) or (3) rolls the whole transaction back: no row, no leaf, no serial (SetLastSerial is in the same transaction), no index or pending-state change. After a COMMIT that published, store the KRL as Revoke does and set `lastProbePublish`.
- **republishIfDue.** The early return for a last publish younger than an hour is skipped only while `probePrompt` is set, the index still holds an unpublished negative certificate and `lastProbePublish` is zero or at least `krlCheckInterval` old (a clock that went back counts as old enough). A flagged tick that is too early publishes nothing and leaves the flag set. After a successful publish by the flag it clears `probePrompt` and sets `lastProbePublish`. Any other publish clears the cause (no unpublished negative is left), so the other publishers are untouched. Immediate and flagged publishes are therefore at least `krlCheckInterval` apart on the signer's clock: at most 60 probe-caused KRL versions an hour, besides the hourly one and any admin publish.
