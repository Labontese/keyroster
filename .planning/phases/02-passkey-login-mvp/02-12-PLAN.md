<objective>
The MVP moment: `keyroster login` puts a short-lived certificate into the user's ssh-agent after the user approves the exact request with their passkey, and the user can SSH into a manually configured host.
- **The CLI** makes an ephemeral key, shows its fingerprint, principals and TTL, and runs the D-12 browser-loopback flow with state and PKCE. It verifies the certificate against the root-pinned user CA and adds it with a lifetime: SSH_AUTH_SOCK on Linux and macOS, keyroster's own agent on Windows.
- **The server** shows the same fingerprint on an approval page, accepts the assertion, and calls the signer only when the CLI redeems the code (mint at redemption, RESEARCH Q2).

**DB.** `0004_login.sql` creates `login_sessions(id TEXT PRIMARY KEY, user_name TEXT NOT NULL, request BLOB NOT NULL, code_challenge TEXT NOT NULL, state TEXT NOT NULL, redirect_port INTEGER NOT NULL CHECK (redirect_port BETWEEN 1024 AND 65535), status TEXT NOT NULL CHECK (status IN ('pending','approved','redeemed')), assertion BLOB, code_hash BLOB UNIQUE, code_expires_us INTEGER, created_us INTEGER NOT NULL, expires_us INTEGER NOT NULL)`. Add the accessors `CreateLogin`, `Login(id, now)`, `ApproveLogin(id, assertion, codeHash, codeExpires, now)` and `RedeemLogin(id, codeHash, now)`:
- **Reaper** (addresses review finding 02-12-F12, the 02-07 `UseNonce` pattern). CreateLogin runs `DELETE FROM login_sessions WHERE status = 'redeemed' OR (expires_us < :now AND (code_expires_us IS NULL OR code_expires_us < :now))` in the same transaction as its insert. Redeemed rows go at once: the signer log is the record, and a deleted row cannot be redeemed again. An approved row whose code is still valid survives past expires_us. With the rate limits below and the 240 s window, the table holds at most a few minutes of begins.
- `Login(id, now)` returns the row whatever its expiry fields say; it is "not found" only when no row exists. Each handler applies its own deadline: the approval page and the assertion route use expires_us (CreatedAt + 240 s), and redeem uses code_expires_us (up to CreatedAt + 290 s). An approved row past expires_us must therefore still redeem while its code is valid; `code_capped_by_signer_window` tests this at +289 s.
- ApproveLogin updates only a row that is `pending` with `expires_us >= now`, and requires rows-affected == 1.
- **RedeemLogin is the single atomic burn:** `UPDATE login_sessions SET status = 'redeemed' WHERE id = ? AND status = 'approved' AND code_hash = ? AND code_expires_us >= ?`. It succeeds only when rows-affected == 1, so a concurrent second redeem gets 0 rows and the uniform 400. Every other redeem check runs before it (see redeem below).

**Server** (internal/server/login.go). Rate limits use the 02-07/02-10 limiters with the 02-10 values: every route 20/min with burst 10 per IP, and the API routes also 10/min per username (addresses 02-12-F12).
- `GET /api/v1/login/options?user=NAME` returns, for an active directory user with at least one credential, `{"server_time": <unix>, "user", "ca_max_ttl_seconds", "roles": [{"name","principals","max_ttl_seconds","extensions"}]}`. Otherwise it returns the uniform 404. This unauthenticated disclosure is accepted as T-02-105 (02-12-F13): the CLI must know the exact principals and TTL before it builds the passkey-signed request, so the response is not cut down.
- `POST /api/v1/login/begin {"request","code_challenge","code_challenge_method","state","redirect_port"}`:
  - `request` is base64 std of `LoginIssueRequest.Marshal()` with no evidence; ParseLoginIssueRequest it, and refuse any evidence;
  - the subject must be an active user;
  - |server now − CreatedAt| ≤ 120 s (the CLI already refuses more than 60 s of skew; 02-12-F15);
  - `code_challenge_method` must be `S256`, `code_challenge` must be 43 base64url characters, `state` 43 base64url characters, and `redirect_port` 1024-65535;
  - id = 16 random bytes in hex; expires = CreatedAt + 240 s (02-12-F15, see the assertion step);
  - return `{"login_id","approval_url": <origin>/login/<id>,"expires_at"}`. `<origin>` comes from `requestOrigin(r, origins)` in internal/server/admin.go, the 02-07 helper that picks the policy origin matching the request's Host, called with the policy origins in force. Write no second origin rule (addresses review finding 02-07-F8 for 02-12). Under a single-origin policy, as in the homelab, it yields that origin.
- `GET /login/{id}` renders login_approve.html for a pending session:
  - the fingerprint `ssh.FingerprintSHA256` of the SubjectKey parsed from the stored request bytes, shown large, with "Approve only if your terminal shows exactly this fingerprint. If you did not just run keyroster login, close this page.";
  - the user, the requested roles (or "all your roles"), each principal, the TTL in human form and the expiry time;
  - the attributes `data-assertion="/api/v1/login/<id>/assertion"`, `data-expires="<unix>"` and `data-options="<JSON: challenge = base64url(Digest()), allowCredentials = the user's directory credential ids, rpId, userVerification "required", timeout 60000>"` (html/template attribute escaping);
  - an error `<p role="alert">` element, as on enroll.html;
  - an expired, approved or redeemed session renders the uniform error page.
- `POST /api/v1/login/{id}/assertion {"credential_id","authenticator_data","client_data_json","signature"}`:
  1. the session must be pending and server now ≤ expires_us (CreatedAt + 240 s);
  2. pre-verify with `webauthn.VerifyAssertion` against the subject's directory credential, the policy RP and origins, with challenge = Digest() (a server-side early error only; the signer re-verifies). On refusal, slog records the verifier's sentinel name (for example `bad_authenticator_data`) and, for authenticator-data refusals, the authenticatorData length and its flags byte in hex. Neither is secret, and 02-14 uses them for the A6 record of an authenticator the verifier refuses (02-01-F5);
  3. ApproveLogin: store `wire.WebAuthnAssertion{...}.Marshal()`, a 32-byte random code (store SHA-256), code_expires = min(now + 120 s, CreatedAt + 290 s), status approved. The server and the signer share one host clock (the signer is reached over its local socket), so with this cap every redemption reaches the signer inside its |now − CreatedAt| ≤ 300 s window. A late approval can no longer produce a code that the signer is bound to refuse (addresses 02-12-F15);
  4. return `{"redirect": "http://127.0.0.1:" + stored port + "/callback?code=" + code + "&state=" + stored state}`.
- `POST /api/v1/login/{id}/redeem {"code","code_verifier"}`. The checks run in this order, so a wrong or malformed verifier never burns the code (addresses review findings 02-12-F1 and 02-12-F14):
  1. code_verifier must be exactly 43 characters from the base64url alphabet `[A-Za-z0-9_-]`, with no padding; otherwise return the uniform 400 before any DB access;
  2. `Login(id, now)`: status approved, SHA-256(code) equal to code_hash (subtle.ConstantTimeCompare), and now ≤ code_expires_us;
  3. require `base64url(SHA-256(code_verifier)) == code_challenge` in constant time;
  4. only now burn the code, with `RedeemLogin(id, SHA-256(code), now)` and rows-affected == 1. Single use still rests on that one conditional UPDATE;
  5. build the stored request with Evidence = [{EvidenceWebAuthnAssertion, stored assertion}];
  6. call `signerclient.Login`;
  7. return `{"certificate": base64 std of the certificate's wire bytes}`.

  A signer refusal (a `*wire.ErrorResponse` with `Code == wire.CodeRefused`, matched with errors.As) returns 403 `{"error": <detail>}`. Any other failure returns the uniform 400 `{"error":"login not redeemable"}`. The code, the code_verifier and the state are never logged or persisted (only SHA-256(code) is stored). slog records the failure class only.

  **A lost redeem response is fail-safe.** If the signer minted but the response never reached the CLI, the certificate is logged before release (VIS-01). It is bound to an ephemeral key that only that CLI process held, and that process zeroes the key on exit. Nothing retries: the code is burnt, and the signer refuses a reused RequestID with `duplicate_request`. The user runs `keyroster login` again, which makes a new key, a new request and one more passkey touch.

**CLI** cmd/keyroster/login.go, `keyroster login [--role R]... [--ttl DURATION] [--no-browser]`:
1. loadConfig (requires `user`); serverclient.New; `Trust(...)` gives the bundle, from which the active user CA key comes.
2. GET options. Keep skew = server_time − local now. When |skew| > 60 s, refuse "your clock differs from the server by Ns; fix it before logging in". Selected roles are --role (each must be among the options) or all of them. Principals are the sorted union, cap = min(role TTLs, ca_max_ttl), and extensions the union. `--ttl` larger than the cap is refused; the default TTL is the cap.
3. Make an `ed25519.GenerateKey` key with crypto/rand, in memory only, and `defer clear(priv)` on the next line, so the key is zeroed on every return path. This follows `defer clear(pass)` in cmd/keyroster/root.go and internal/rootceremony/keygen.go, and is best effort (addresses review finding 02-12-F17). Both agent adapters reach the agent through `agent.NewClient` over a connection (socket or pipe), so the key bytes are on the wire before clear runs. Test fakes must likewise be served over a connection (`net.Pipe` or a socket with `agent.ServeAgent`), never called in-process, because an in-process keyring would keep the same slice. Build the request with RequestID 16 random bytes and CreatedAt now.
4. Print to stderr: `Login for <user>: principals <list>, valid <ttl>`, `Key fingerprint: SHA256:…` and "Approve in your browser only if it shows this fingerprint."
5. code_verifier = 32 random bytes in base64url, code_challenge = base64url(SHA-256(verifier)), state = 32 random bytes in base64url.
6. loopback.go: `net.Listen("tcp", "127.0.0.1:0")`. Its handler accepts only `GET /callback` with r.Host equal to `127.0.0.1:<port>` exactly (else 400), and state equal through subtle.ConstantTimeCompare (else 400, keep waiting). It answers a small HTML page "keyroster: approved, you can close this tab" with Cache-Control no-store, delivers the code once, then shuts down.
7. POST begin and print the approval URL. Unless --no-browser, call `openBrowser(url)`: xdg-open on Linux, `open` on macOS, `rundll32 url.dll,FileProtocolHandler` on Windows, nothing elsewhere. A failure to open is only a warning.
8. Wait for the callback until the server's approval deadline on the local clock, `expires_at − skew + 5 s`; on timeout fail with "login not approved in time". This replaces the earlier fixed CreatedAt + 270 s, which could end the wait before the server's window closed (02-12-F15).
9. POST redeem. Any redeem failure ends the command with exit 1 and `login not completed: <reason>; run keyroster login again`: an HTTP error, a 400, a 403 (shown as "refused by the signer: <detail>"), a timeout, or a lost or unparsable response. It never retries redeem (addresses 02-12-F1; the lost-response case is fail-safe, see redeem above). Then read `now := time.Now()` **once**, and use that single value for every time check below and for the lifetime in step 10 (addresses 02-12-F2). Parse the certificate and verify:
   - a user certificate whose `SignatureKey` equals the user CA;
   - `Key` equal to the ephemeral public key;
   - ValidPrincipals equal to the requested set exactly;
   - KeyId parses (cert.ParseKeyID) as kr2 with Subject = user and Request = hex(RequestID);
   - ValidBefore − ValidAfter ≤ TTL + 300 (cert.Build's five-minute backdate);
   - remaining = ValidBefore − ceil(now), where ceil rounds a fractional second up, so the lifetime never exceeds the certificate's remaining validity. Require remaining ≥ 60, which also guarantees remaining > 0.
10. Add to the agent (loginagent_*.go) `agent.AddedKey{PrivateKey, Certificate, LifetimeSecs: uint32(remaining), Comment: KeyId}`:
    - Unix: dialAgent over SSH_AUTH_SOCK. When it is unset, fail with "start ssh-agent (eval $(ssh-agent)) and retry; keyroster never writes the key to a file". Apply the A3 decision from 02-02.
    - Windows: `winagent.Ensure(ctx, os.Executable())`. It returns only a connection the agent already counts as active, so no extra retry follows Add. Its errors, notably `winagent.ErrOwnerUnverifiable` (an agent started elevated), reach the user with their help text unchanged and are not wrapped into the lifetime message below.
    - On an Add error, return it wrapped with "the agent refused the key with a lifetime constraint; not retrying without it". Then List(); the certificate blob must be present, else fail "the agent dropped the certificate".
11. Print the principals, `Serial: <n>`, `Key ID: <kr2 key ID>`, the expiry time in local time and, on Windows, `Use: ssh -o IdentityAgent=<pipe> ...` or the ~/.ssh/config line. The serial and key ID let the owner and the 02-14 checks tie a login to its signer log entry and its sshd journal line.
