<objective>
Give admins a safe way to start an enrollment.
- `keyroster user add alice` reaches the server through an SSHSIG-authenticated admin API: payloads are authenticated, not pipes, and the keys are the policy's admin keys, the same machinery as Phase 1 admin evidence (D-02).
- It creates a pending account and prints the invite URL plus the user's `keyroster init` line.
- The invite page greets the invitee.

Nothing on the server is authority: the account stays unusable until 02-09 binds a credential through an admin-signed directory.

**internal/adminauth** (stdlib plus internal/sshsig; never imported by the signer):
- Constants: `Namespace = "keyroster/admin-api/v1"`, `HeaderTime = "Keyroster-Admin-Time"`, `HeaderNonce = "Keyroster-Admin-Nonce"`, `HeaderSignature = "Keyroster-Admin-Signature"`, `MaxSkew = 120 * time.Second`.
- `Message(method, path string, bodySHA256 [32]byte, unix int64, nonce string) []byte` is exactly `keyroster/admin-api/v1\n<METHOD>\n<path incl. query>\n<hex sha256>\n<decimal seconds>\n<32 lowercase hex nonce>\n`.
- `Sign(signer ssh.Signer, method, path string, body []byte, now time.Time) (http.Header, error)` uses sshsig.Sign under Namespace, with the signature header holding base64 std of the armored SSHSIG.
- `Verify(h http.Header, method, path string, body []byte, now time.Time, admins []trust.AdminKey) (adminName string, nonce string, err error)` checks the time window, the nonce format, the signature parse, that the key equals an admin's key (by fingerprint and exact key, as verifyAdminEvidence does), and the namespace.
- Path canonicalisation (addresses review finding 02-07-F12): `path` is the raw request-target, path plus query exactly as sent on the wire, never normalised, cleaned or unescaped. The client passes the `URL.RequestURI()` of the request it actually sends, and the server passes `r.RequestURI`. Neither side ever uses the decoded path field of the parsed URL or its escaped-path method. State this in the package doc comment.

**internal/serverdb** mirrors signerdb:
- an embedded `migrations/0001_server.sql` with tables `pending_users(name TEXT PRIMARY KEY, user_handle BLOB NOT NULL UNIQUE, invite_hash BLOB NOT NULL UNIQUE, invite_expires_us INTEGER NOT NULL, created_us INTEGER NOT NULL, created_by TEXT NOT NULL)` and `admin_nonces(nonce TEXT PRIMARY KEY, expires_us INTEGER NOT NULL)`, with a header comment stating that nothing here is authority;
- `Open(path)` with WAL, synchronous FULL, one connection, PRAGMA user_version and refusing a newer DB, the file mode 0600;
- accessors `CreatePendingUser`, `ReplaceInvite`, `PendingUserByInvite(hash, now)`, `PendingUser(name)`, `UseNonce(nonce, expires, now)` (insert; a duplicate means replay; it also deletes expired rows).
- `PendingUserByInvite(hash, now)` returns the pending row whose invite_hash matches and whose invite has not expired. Under this migration no invite can be used yet; 02-08 adds the `invite_used_us` column and extends this accessor to require an unused invite as well (cross-plan audit).
- `ReplaceInvite(name string, inviteHash []byte, expiresUS int64) error` updates the pending row in place: new invite_hash and expiry, same user_handle. It is last-writer-wins: the single connection serialises concurrent reinvites, so exactly one token stays valid and every earlier one stops matching. 02-08 extends it in the same transaction to reset invite_used_us and drop the user's registration sessions and pending credential (reinvite semantics, addresses review finding 02-07-F5).

- ratelimit.go: a per-client `rate.Limiter` map with LRU-bounded size (10 000 entries) and idle eviction. Admin routes get 60/min with burst 20, and invite routes 30/min with burst 10. These defaults live in a limits field of the server options, so server tests can raise them (02-08's concurrency tests do). A limited request returns 429 with Retry-After. Addresses review finding 02-07-F6:
  - `clientKey(r)` takes the host of `r.RemoteAddr` only and never reads X-Forwarded-For or Forwarded, because the server has no proxy in front of it. An IPv4 address (or IPv4-mapped IPv6) is its own key. Any other IPv6 address is keyed by its /64 prefix (`netip.Addr.Prefix(64)`), so one host rotating addresses in its /64 shares one bucket.
  - Each route class also has one global limiter as a coarse backstop, at ten times the per-client rate and burst (admin 600/min burst 200, invite 300/min burst 100). Either limiter refusing gives 429.
  - The limiter is best-effort DoS damping only. Authenticity rests on SSHSIG with single-use nonces (admin) and on 256-bit hashed tokens (invites); see T-02-36.
- admin.go:
  - `requireAdminLimit(limit int64, next)` is the middleware. `requireAdmin(next)` is exactly `requireAdminLimit(maxAdminBody, next)`, where `maxAdminBody` = 1 MiB + 64 KiB is the default body limit of every admin route. Every route in this plan and in 02-08 uses the `requireAdmin(next)` form; only 02-09's directory install route names another limit (plan checker, iteration 2).
  - Size gate, before any signature work. The middleware reads the whole body through `http.MaxBytesReader` with `limit`: the SSHSIG covers the body's SHA-256, so the body has to be read before anything can be verified, and the limit bounds that read. A body over the limit (the read fails with `*http.MaxBytesError`) gets 413 `{"error":"request body too large"}` at once and a log line with the route and the limit: adminauth.Verify does not run, no nonce is consumed and the handler is not called. The status is 413 and not the uniform 401 on purpose. AdminJSON reports every 401 as `admin authentication failed`, in some cases with a clock hint, which would send an admin with an oversized body looking in the wrong place. The limit is a public constant and the check reads no secret, so the status tells an unauthenticated caller nothing.
  - The middleware then calls adminauth.Verify with `r.RequestURI` as the path and the admins of the cached policy. UseNonce must be fresh. Any authentication failure returns 401 `{"error":"admin authentication failed"}` and logs the reason with slog, never the token or signature. The request reaches the handler with the admin name in its context.
  - requireAdmin re-attaches the verified bytes as `r.Body` (an `io.NopCloser` over a `bytes.Reader` of the buffer it verified), so the handler decodes exactly the body that was signed (addresses review finding 02-07-F7).
  - The nonce is consumed (UseNonce) before the handler runs, on purpose: this closes the window in which a captured request could be replayed while the first copy is still running. A failed admin request (5xx, 409, signer unreachable) is therefore retried only by signing it again with a new nonce. AdminJSON signs on every call and never resends old headers, and serverclient has no transport-level retry (addresses review finding 02-07-F1).
  - `POST /api/v1/admin/users` with body `{"name":..., "reinvite":false}`:
    1. validate the name with the directory user-name rule (directory package);
    2. look the name up in both places: the installed directory, read with `s.signer.GetDirectory` (the seam method this plan adds, see below), and pending_users (`PendingUser`). Then decide in this fixed order, in which the pending check always comes first (cross-plan audit):
       - without reinvite, refuse 409 if the name is pending or in the installed directory;
       - with reinvite and a pending row, the row gets a new token through ReplaceInvite: the old one becomes invalid, and the row keeps its user_handle. This branch is taken whenever a pending row exists, also when the name is in the installed directory as well. That state is normal and long-lived: it is a directory user whose extra-passkey invite is still open, which 02-09's cleanup deliberately leaves in place. The branch never inserts, so the pending_users primary key cannot conflict;
       - with reinvite and no pending row, a name in the installed directory gets a new pending row for one additional credential, with a fresh 32-byte random user_handle: the installed directory stores no user handle, and sign-in is username-first, so the handle never takes part in authentication (addresses review finding 02-07-F5);
       - with reinvite and the name in neither place, the request continues as a plain add;
    3. make a 32-byte random token (crypto/rand, base64url, no padding) and store its SHA-256;
    4. set the expiry to now + 24 h, and give a new user a 32-byte random user_handle;
    5. return 201 `{"name","invite_url","expires_at"}`, with invite_url = origin + `/enroll/` + token. `requestOrigin(r, origins)` (in admin.go, shared so 02-12 reuses it for approval_url) picks the policy origin equal to `https://` + r.Host (with a `:443` suffix removed); when none matches, it uses the first sorted policy origin. Every candidate is a policy origin, so the choice cannot weaken the signer's origin check. It only makes the link point at the port the admin actually reached (addresses review finding 02-07-F8).
- invite.go `GET /enroll/{token}` hashes the token and looks up a pending, unexpired invite. It renders enroll.html with the user name, the rp_id, the expiry and the text "Your admin will give you a keyroster init command; run it before keyroster login". An unknown or expired token renders the uniform error page with 404. The page has no script yet; 02-08 adds the registration ceremony.

**Client.**

The PEM is public data; init still requires `--tls-pin` to match the observed root. Every interpolated value comes from an alphabet with no shell metacharacters (validated server URL, `sha256/` and `SHA256:` base64 pins, an int, the directory name rule), so the line needs no quoting.
