<objective>
Make every login certificate provable after the fact, and give operators the tool that adds the RP to a running installation.
1. `keyroster root successor-policy` builds the root-signed policy successor that carries the WebAuthn RP. The homelab needs it in 02-13, and it is the only supported way to add or change the RP.
2. `keyroster audit verify` verifies the new log kinds. Each directory install must be quorum-signed under the policy in force. Each login certificate must have been approved by that user's bound passkey over the exact logged request, with principals and TTL the directory allows.

Purpose:
- KEY-02 and AUTHZ-01, verified by an auditor, not only enforced by the signer. A compromised signer holding the log key still cannot log an unauthorized login issuance that passes audit. This serves the core value, full visibility.
- It also ends the 02-01 interim state. From 02-01 until this plan, audit verify refuses every log that holds a directory_install or login_issue entry, at that entry, with `not verifiable by this version` (the default branch 02-01 added to the kind switch). This plan gives both kinds real checks. The default refusal stays for any later kind.

Output: the successor-policy subcommand, the audit checks, a tamper suite, an e2e across a live policy change, a runbook section, and a PR through the merge gate.
</objective>

**`keyroster root successor-policy`** (cmd/keyroster/root.go: a new case in runRoot's switch and a usage-line update). The command:
- takes the flags `--prev FILE`, the canonical policy in force (policy.json from the bundle directory in force), `--out FILE` (must not exist), `--webauthn-rp-id HOST` (required in Phase 2, since the RP is the only field this command changes) and a repeatable `--webauthn-origin URL` (default `https://HOST`);
- runs trust.ParsePolicy on --prev, then copies it with Version + 1, Prev = trust.SHA256Hex(prev bytes) and WebAuthn set;
- validates the result and writes it canonically;
- refuses when the RP equals the current one ("nothing to change");
- prints the old and new rp_id and origins, the new policy's SHA-256, and this warning to stderr: "WARNING: rp_id is a one-way setting. Every passkey enrolled under it works only for that exact hostname; renaming the host or changing rp_id makes every enrolled passkey unusable."

Other policy fields (admins, quorum, profiles, timelock) are not editable here; quorum-gated policy change is Phase 4 (AUTHZ-03). Say so in the usage text.

The checks:
- `directory_install`: decode DirectoryInstallBody; then run directory.Parse, CheckSuccessor against the directory in force, VerifySignatures against the policy in force (≥ AdminQuorum), and CheckPolicy. Require the body's PolicyVersion to equal the policy in force and its Version to equal the parsed version. Then make it the directory in force. Each failure returns an error of the form `entry <index> (directory_install): <check>`.
- `login_issue`: decode LoginIssueBody and parse Request with ParseLoginIssueSigningBytes. Require all of the following:
  - DirectoryVersion equals the directory in force, and PolicyVersion the policy in force;
  - the directory verifies under the policy in force at this leaf; it may have been re-checked after a later bundle_install, which mirrors the signer's directory_not_authorized rule. The walk keeps one cached result for the current (directory, policy) pair: it runs VerifySignatures and CheckPolicy for that pair only when one side changes, at a directory_install entry and after each bundle_install entry, and every login_issue entry reuses the stored result (addresses review finding 02-04-F8). A directory installed under an earlier policy stays in force across a policy change that still authorizes it, such as one that only adds the RP;
  - policy.WebAuthn is non-nil;
  - exactly one evidence item, of type webauthn-assertion/v1, which parses;
  - the directory's credential for (user, credential ID) exists for an active user;
  - webauthn.VerifyAssertion(cred, rp_id, origins, SHA-256(Request), assertion) returns nil;
  - Authorize(user, roles) gives principals equal to the request's, with ValidForSeconds ≤ min(MaxTTLSeconds, the user profile cap) and extensions inside the grant;
  - the certificate is a user certificate signed by the active user CA in force, its Key equals SubjectKey, and its ValidPrincipals equal the request principals;
  - its validity window is what cert.Build produces for ValidForSeconds, the rule already applied to kind 1;
  - KeyId parses as kr2 with sub = Subject, req = hex(RequestID), pol, dir, roles = grant roles and ser = Serial;
  - serial ordering is as for kind 1, in one sequence shared with kind 1: a login serial must exceed the last serial of either kind, and the next issue serial must exceed it. The signer issues both from one serial counter and one issuance table, and its start-up check counts both kinds together (02-01's logstate rule, T-02-116). Two pieces of walk state carry the rule, and both kinds update both: the last serial, and whether any serial has been seen. The second is `rep.Serials > 0` today, which counts issue leaves only; left like that, a log whose first certificate is a login would accept a later issue entry with a lower serial. Give it its own variable in the walk and pass that to checkIssue;
  - |entry time − CreatedAt| ≤ 300 s.

  Each failure returns an error of the form `entry <index> (login_issue): <check>`.
