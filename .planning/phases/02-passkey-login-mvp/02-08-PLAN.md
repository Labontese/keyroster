<objective>
Let an invited user register a passkey. The flow:
1. The invite page runs the WebAuthn create ceremony with one hand-written JS file.
2. go-webauthn, server only and reviewed by the owner first, verifies the attestation-none registration.
3. The server keeps the credential as a **pending** SPKI with its fingerprint, shown to the user.
4. The admin sees the same fingerprint with `keyroster user pending`.

The credential grants nothing until 02-09's admin-signed directory binds it.

Purpose:
- AUTH-01: every account must register at least one passkey.
- UI-01: the registration page.
- D-03 steps 2 and 3, and D-05: any authenticator, UV required, attestation none, BE/BS recorded.
- D-17: CBOR stays out of the signer.

Output: the registration endpoints and page, app.js, `keyroster user pending`, a differential oracle for the signer's verifier, dependency bans, and a PR through the merge gate.
</objective>

Add the accessors to db.go:
- `CreateRegistrationSession(inviteHash []byte, challenge string, session []byte, expiresUS, nowUS int64) error`. It first deletes every expired session row. It then refuses with `ErrTooManySessions` when the invite already has 16 unexpired sessions, and otherwise inserts.
- `ConsumeRegistrationSession(inviteHash []byte, challenge string, nowUS int64) ([]byte, error)` runs `DELETE FROM registration_sessions WHERE invite_hash = ? AND challenge = ? RETURNING session, expires_us`. No row gives `ErrNotFound`, and an expired row (already deleted by the statement) gives `ErrExpired`. A session can therefore be consumed exactly once, atomically.
- `BindPendingCredential(inviteHash []byte, nowUS int64, cred PendingCredential) error` runs one transaction:
  1. `UPDATE pending_users SET invite_used_us = ? WHERE invite_hash = ? AND invite_used_us IS NULL AND invite_expires_us > ? RETURNING name`. Unless exactly one row comes back, it rolls back and returns `ErrInviteNotValid`; the invite was used, expired or replaced by a reinvite;
  2. inserts pending_credentials for that name. A primary-key or one-per-user constraint failure rolls back and returns `ErrDuplicateCredential`.

- Extend 02-07's `ReplaceInvite` (reinvite semantics; addresses review findings 02-08-F7 and 02-07-F5). In the same transaction as the invite_hash and expiry swap, it sets `invite_used_us = NULL`, deletes the registration_sessions rows of the old invite_hash, and deletes the user's pending_credentials. An unapproved credential from a replaced invite is discarded, and the user registers again under the new invite. The pending row keeps its user_handle, so re-registering on the same authenticator replaces the orphaned passkey there (UNVERIFIED: authenticator behaviour, not exercised in this phase). The tested part is server-side: 02-07's `reinvite_directory_user_with_pending_row` asserts that the row keeps its user_handle.

A proposal directory that an admin wrote with `--out` before the reinvite still names the discarded credential, and nothing here can reach that file. 02-09's install handler therefore refuses any install that newly binds a credential which is not pending for that user (`credential_not_pending`).

- enroll.go, the refusal log line (addresses review finding 02-08-R2-F10). Every answer of begin or finish that is not a 2xx writes exactly one line through the server's logger (02-06's `Config.Logger`, slog), with the message `enroll refused` and exactly these four attributes: `route` (`begin` or `finish`), `reason` (one code from the list below), `user` (the pending user's name once the handler has it, which is after begin's lookup and, in finish, after the lookup that supplies CreateCredential's user argument; otherwise empty) and `err` (the underlying error's `Error()` text, or empty). One helper, `logEnrollRefusal`, writes it; no call site builds its own line. The level is info for a refusal and error for the two server-side failures, `signer_unavailable` and `internal_error`.
  - Reason codes, a closed list. Every non-2xx answer has exactly one of them (plan checker, Round 2 revision):
    - `invite_not_valid`: begin's lookup found no current invite, finish's own lookup of the pending user for the invite found none, or BindPendingCredential returned ErrInviteNotValid;
    - `too_many_sessions`: ErrTooManySessions at begin;
    - `bad_request`: the finish body does not parse;
    - `session_not_found`: ErrNotFound or ErrExpired from ConsumeRegistrationSession;
    - `verify_failed`: go-webauthn refuses the registration (step 3). This includes a key whose algorithm is outside the three offered: go-webauthn checks the credential's algorithm against the session's offered list itself (v0.18.2 `protocol/attestation.go`, its step 16);

    - `duplicate_credential`: step 5, or ErrDuplicateCredential in step 6;
    - `signer_unavailable`: currentStatus or `s.signer.GetDirectory` failed (the 503 answer);
    - `internal_error`: any other failure the handler answers with a 5xx, for example a database error. Its `err` is the error's `Error()` text, under the same rule as below.
  - Never in the line: the invite token or its hash, the challenge, the session data, the credential ID, the SPKI, the attestation object, clientDataJSON or any other part of the request body. No secret and no credential material is logged.
  - For a go-webauthn `*protocol.Error`, `err` is its `Error()` text, which is the `Details` field alone. Its debug field is never logged in any form, neither the field itself nor the struct printed or marshalled: on a challenge mismatch it quotes the expected and the received challenge (v0.18.2 `protocol/errors.go` and `protocol/client.go`, read in the module cache while this plan was revised).
