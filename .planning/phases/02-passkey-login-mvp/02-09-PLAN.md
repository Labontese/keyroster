<objective>
Close the enrollment loop. `keyroster user approve` binds a registered passkey through an **admin-signed directory version**, the only thing the signer treats as authority. Every directory edit uses one pipeline with the same safeguards:
- the trust bundle is verified against the root pins;
- the installed directory is verified locally against the policy admins;
- the successor is built, validated and diffed;
- it is signed with the admin's SSH key;
- it is installed through the server, or saved as a proposal for co-signing when the quorum needs more admins.

The first admin enrolls the same way (D-04).

Purpose:
- AUTH-01 and success criterion 1: an account is unusable until the user registers a passkey and an admin binds it.
- KEY-02: authority is a quorum-signed directory version.
- D-01 to D-04.

02-11's role, group and host-group commands reuse the pipeline.

Output: the pipeline, user approve/list/disable/enable, directory show/sign/install, server forwarding and mirror, an enrollment runbook, and a PR through the merge gate.
</objective>

In chain mode it behaves like the signer for the version chain: it accepts a version whose prev is the SHA-256 of the bytes it holds (or genesis when it holds none), holds the new bytes from then on, and reports them from Status and GetDirectory; any other version gets the refusal `*wire.ErrorResponse{Code: wire.CodeRefused, Message: "directory_version_chain"}`, the type signerclient returns. In both modes it keeps the last request it was given, so a test can compare the bytes the server forwarded. Two additions serve Task 2's `TestDirectoryInstallPending` (02-09-R2-F1, 02-09-R2-F4): 02-06's blocking hook also applies to this method. It can be armed for InstallDirectory alone, leaving Status and GetDirectory unheld, and it reports when a call has entered it, so a test can hold an install inside the signer call and know that it is there; and chain mode has a switch `loseAnswer`, under which the fake accepts and holds the version and then returns a transport error in place of the response, as when the signer commits and its reply is lost.

  Everything in directory.go and admin.go reaches the signer as `s.signer.GetDirectory` (added in 02-07) and `s.signer.InstallDirectory`. signer.go stays the only file in internal/server that imports the signerclient package.
- internal/server/directory.go keeps a directory mirror behind one accessor, `(*Server).currentDirectory(ctx) (*directoryView, error)`. Every reader goes through it: the admin endpoints here, and 02-10's sign-in and withSession. Fail-closed rule (coordinator follow-up for 02-10's mirror truth):
  - it reads signer state **only** through 02-06's `(*Server).currentStatus(ctx)`, the one status cache: answers at most 5 s old, and a failed refresh gives an error and no stale data. The mirror keeps no status cache, TTL or grace window of its own. It holds only the directory bytes, sigs and parsed Directory for a single SHA-256;
  - currentStatus returning an error makes currentDirectory return that error;
  - when Status reports no installed directory (version 0), it returns an empty view (version 0) without calling the signer;
  - when Status's directory SHA-256 equals the held entry's SHA-256, it returns the held entry;
  - otherwise it drops the held entry first, then calls `s.signer.GetDirectory`. If that call fails, or returns a directory whose SHA-256 (of the returned bytes) differs from Status's directory SHA-256, it returns an error (`errMirrorStale`) and holds nothing. It never serves the previous version. A mismatch also covers an install that landed between the status read and the fetch; that request fails closed. On a mismatch the mirror also calls `s.dropStatus()`, because the status it read is then known to be out of date; the next request reads Status afresh and converges at once;
  - otherwise it parses the bytes with directory.Parse, holds them under that SHA-256 and returns them.
  - The install handler below does not write the mirror. It calls 02-06's `dropStatus` instead (step 4 of the POST route), so the next currentStatus asks the signer, reports the new SHA-256, and the mirror follows on the very next read (cross-plan audit, BLOCKER). A version installed through this server therefore never waits for the status entry to age out. Only a version installed without this server, directly on the signer socket, does: readers pick it up within 5 s.

  - Why this covers the signer's cap: a request the signer's install frame can carry has Directory plus Sigs below `wire.MaxDirectoryFrame` bytes (02-03's frame rule), and two separately encoded base64 fields are at most 4 bytes longer than one field of their combined length. Every install the signer could accept therefore fits, including a directory of exactly `wire.MaxDirectory` bytes with 64 KiB of signatures, which is 1 485 514 bytes as JSON.

One byte over it gets 413 `{"error":"request body too large"}`: no adminauth.Verify, no nonce consumed, no call to the signer. The handler adds no size limit of its own. What installs is still decided by the signer's own caps; this limit only bounds what the server reads.

It orders the two operations that could otherwise interleave: a directory install, which checks pending rows, forwards and then cleans them up, and `user add --reinvite`, which discards a pending credential.
  - Install side: the POST handler below locks `pendingMu` before its step 1 and holds it through step 5. It unlocks by defer, so every return path releases it. What the finding needs is steps 3 to 5 (check, forward, cleanup). Steps 1 and 2 are inside as well, so that newlyBound is always computed against the base in force when the check runs: a second install that waited for the lock then gets the signer's `directory_version_chain` for a version already installed, and not a misleading `credential_not_pending`.
  - Reinvite side: this plan edits 02-07's `POST /api/v1/admin/users` handler in admin.go. A request whose body has `reinvite` true locks `pendingMu` before the lookups of 02-07's step 2 and holds it until its row is written (ReplaceInvite or CreatePendingUser). The lock must cover the lookups: taken only around the write, an install could delete the row between the lookup and the update. A plain add, with `reinvite` false, does not take the lock, because it discards nothing an install checks.
  - Lock order: `pendingMu` is always the outermost lock. A handler takes it after requireAdmin has finished, and no code that holds the status-cache mutex or the mirror's own lock ever takes it. Under it the two handlers call `currentStatus`, `dropStatus`, `s.signer.GetDirectory`, `s.signer.InstallDirectory` and the database as before.

The database's single connection is not held across the signer call, so every handler that does not take the lock (invite pages, registration, admin nonces, the directory reads) keeps working while an install is in flight. Only a reinvite or a second install waits, and only for the holder's signer calls. An install makes up to three of them under the lock: a Status refresh inside currentStatus (02-06 gives it a 3 s timeout), a GetDirectory when the mirror has to refetch, and InstallDirectory. A reinvite makes one, its GetDirectory. signerclient bounds each call whose context has no deadline with its `defaultTimeout` of 10 s (internal/signerclient/client.go). A waiter behind one install therefore waits at most about 23 s (3 + 10 + 10) for the signer, plus up to 3 s when `dropStatus` has to wait for a refresh another request has in flight. That worst case needs a signer that hangs on every call; an earlier deadline on the request context shortens it.
  - The winner is whichever takes the lock first, and both orders end in a state that a serial run also produces:

The waiting reinvite then finds a directory user with no pending row and takes 02-07's branch for one additional passkey, with a fresh user_handle. The bound passkey stays bound in the directory, and the new pending row carries a user_handle other than the old one; `reinvite_waits_for_running_install` asserts both. That a registration under a different user handle leaves the bound passkey in place on the authenticator is authenticator behaviour under the WebAuthn rules. No test in this phase exercises it with a real authenticator (UNVERIFIED).

Its steps, in this order:

  2. **newlyBound.** Parse the posted directory with directory.Parse and compute `newlyBound`: the canonical credential IDs present in the posted version and absent from that base, each with the user that holds it in the posted version. newlyBound is always a subset of the posted version's credential IDs, so nothing unbound can be deleted later. Keep `bound` as well: every credential ID of the posted version with the user that holds it, as `[]serverdb.Binding` (fields `ID` and `User`). Step 3 checks newlyBound and step 5 cleans up with bound (02-09-R2-F4). A posted document that does not parse has an empty newlyBound, an empty bound, and is still forwarded unchanged, so the signer refuses it as `directory_invalid` and logs the refusal. Addresses review finding 02-09-F6.
  3. **Pending check** (cross-plan audit). Every newlyBound credential must be a pending credential of that same user: `serverdb.PendingCredentialUser(id string) (userName string, err error)`, a new read accessor, must return that user's name (it returns ErrNotFound when no pending credential has the id). Otherwise answer 409 `{"error":"credential_not_pending"}` and forward nothing.
     - This is what makes a completed reinvite final for installs through this server: once a reinvite has returned, no install through the server can bind the credential it discarded. 02-08's ReplaceInvite deletes the user's unapproved pending credential, but a proposal written earlier with `--out`, or waiting for a co-signer, still names it and is not linked to the pending row.
     - Steps 1 to 5 run under `pendingMu` (the pending-lock bullet above), so a reinvite cannot land between this check and the forward. A reinvite that arrives while an install holds the lock waits, and that install wins (02-09-R2-F1).
     - The check only ever refuses. A pending row still grants nothing (D-03); the signer's rules are unchanged.
     - A version that binds no new credential (role, group, host-group, disable and enable edits) has an empty newlyBound and passes untouched.
  4. **Forward, then drop the status cache** (cross-plan audit, BLOCKER). Call `s.signer.InstallDirectory`, and call `s.dropStatus()` as soon as it returns, whatever it returned: accepted, refused, or a transport error whose outcome is unknown. The next currentStatus then asks the signer, so the next read (the next edit's base, the next sign-in) sees the installed version at once. After a `directory_version_chain` refusal the same drop means the server's base is re-read at once, so the CLI's advice to re-run works without a wait, also when the other version was installed without this server.
  5. **On success**, call `serverdb.DeleteBound(bound []serverdb.Binding, nowUS int64) error` with `bound` from step 2 and return `{"version","sha256","leaf_index"}`.
     - Cleanup failure (addresses review finding 02-09-R2-F4). If DeleteBound returns an error, the handler logs one slog line at level error with the message `pending_cleanup_failed`, the installed version and the error, and still answers 200 with that same body. The signer has installed the version, and a 500 here would tell the admin the opposite.
  - `DeleteBound` runs one transaction. For each binding it deletes the pending_credentials row whose id **and** user_name both equal the binding's (`WHERE id = ? AND user_name = ?`). For each user_name whose row it deleted, it then deletes the pending_users row only when that user has no remaining pending credential **and** the invite is not open (`invite_used_us IS NOT NULL OR invite_expires_us <= now`). It never touches a pending account whose invite is unused and unexpired, for example a directory user's open extra-passkey invite, and never another user's pending credential.
    - It is self-healing (02-09-R2-F4). It covers every binding of the installed version, not only the ones this install added, so a pending credential left behind by an earlier install is removed by the next accepted install through this server. Such a row is left when that install's cleanup failed, or when the signer installed the version and its answer was lost. With a newlyBound-only cleanup it would never be removed: its ID is in the base from then on, so it is never newly bound again.

**cmd/keyroster/dirpipe.go.**
- `fetchVerifiedDirectory(ctx, env cliEnv, adminKey string) (*verifiedDirectory, error)` is the one shared fetch-and-verify helper (addresses review finding 02-11-F7). `verifiedDirectory` holds `Version uint64; Doc, Sigs []byte; Dir *directory.Directory; Policy *trust.Policy; Signers []string; SHA256 string`. - `editDirectory(ctx, env cliEnv, opts editOpts, mutate func(d *directory.Directory, pol *trust.Policy) error) error`. opts holds `Yes bool`, `Out string` and `AdminKey string`. The steps:
1. (fetchVerifiedDirectory) loadConfig; serverclient.New; `Trust(cfg.TrustPins, cfg.TrustThreshold)` returns the bundle and policy.
2. (fetchVerifiedDirectory) GET /api/v1/admin/directory. When version > 0: `directory.Parse(doc)` and `directory.VerifySignatures(doc, sigs, policy)`, which must meet the quorum. On failure refuse with "the server's directory is not signed by the policy admins; refusing to build on it". When version is 0, the helper returns the version-0 form above (a non-nil result with a nil `Dir`), and the base is nil.
3. next = a deep copy of the base (or a new Directory with Version 1, Prev GenesisPrev and empty lists) with Version + 1 and Prev = trust.SHA256Hex(base bytes). Call mutate, then Sort, Validate and CheckPolicy.
4. Print Diff and the next version's SHA-256. Prompt `Sign directory version N? [y/N]` on the TTY unless --yes. With no TTY and no --yes, refuse. This rule is `confirmSign`, defined after these steps and shared with `directory sign`.
5. Sign `next.Canonical()` with sshsig under directory.Namespace using the admin key from --admin-key or config.AdminKey, through agentSigner over dialAgent.
6. If `policy.AdminQuorum > 1` or --out is set: write `<Out>/directory.json` and `<Out>/directory.json.sigs` (armored SSHSIG blocks, newline-separated, the root sign convention) plus `<Out>/base.sha256`. 7. A 409 `directory_version_chain` becomes the error "the directory changed since it was read (another admin installed a version); re-run this command". That advice fits only this direct path, which rebuilds from the current base. The re-run can follow at once: the server dropped its status cache when the signer refused (POST step 4), so it serves the current base.
8. A 409 `credential_not_pending` (POST step 3) becomes the error "the passkey this change binds is no longer pending for its user (the user was re-invited, or the invite was replaced). On this direct path it can only happen when a reinvite completes between this command's pending lookup and the server's check.
- `confirmSign(yes bool, version uint64, stdout io.Writer) error` in dirpipe.go is the one confirmation rule for every command that signs a directory version: step 4 above and `directory sign` (addresses review finding 02-09-R2-F10).
