<objective>
Close the enrollment loop. `keyroster user approve` binds a registered passkey through an **admin-signed directory version**, the only thing the signer treats as authority. Every directory edit uses one pipeline with the same safeguards:
- the trust bundle is verified against the root pins;
- the installed directory is verified locally against the policy admins;
- the successor is built, validated and diffed;
- it is signed with the admin's SSH key;
- it is installed through the server, or saved as a proposal for co-signing when the quorum needs more admins.

The first admin enrolls the same way (D-04).

Purpose:
- AUTH-01 and success criterion 1: an account is unusable until the user registers a passkey and an admin binds it.
- KEY-02: authority is a quorum-signed directory version.
- D-01 to D-04.

The role and group commands of 02-10 reuse the pipeline.

Output: the pipeline, user approve/list/disable/enable, directory show/sign/install, server forwarding and mirror, an enrollment runbook, and a PR through the merge gate.
</objective>

**Server.**
- internal/server/directory.go keeps a directory mirror behind one accessor, `(*Server).currentDirectory(ctx) (*directoryView, error)`. Every reader goes through it: the admin endpoints here, and 02-10's sign-in and withSession. Fail-closed rule (coordinator follow-up for 02-10's mirror truth):
  - it reads signer state **only** through 02-06's `(*Server).currentStatus(ctx)`, the one status cache: answers at most 5 s old, and a failed refresh gives an error and no stale data. The mirror keeps no status cache, TTL or grace window of its own. It holds only the directory bytes, sigs and parsed Directory for a single SHA-256;
  - currentStatus returning an error makes currentDirectory return that error;
  - when Status reports no installed directory (version 0), it returns an empty view (version 0) without calling the signer;
  - when Status's directory SHA-256 equals the held entry's SHA-256, it returns the held entry;
  - otherwise it drops the held entry first, then calls signerclient.GetDirectory. If that call fails, or returns a directory whose SHA-256 (of the returned bytes) differs from Status's directory SHA-256, it returns an error (`errMirrorStale`) and holds nothing. It never serves the previous version. A mismatch also covers an install that landed between the status read and the fetch; that request fails closed, and the next status refresh (at most 5 s) converges;
  - otherwise it parses the bytes with directory.Parse, holds them under that SHA-256 and returns them.
  - The install handler below does not write the mirror. After an install, the next currentStatus refresh (at most 5 s) reports the new SHA-256 and the mirror follows. A newly installed version therefore reaches readers within the 5 s status window, never older.
- `GET /api/v1/admin/directory` (requireAdmin) returns `{"version","directory","sigs","authorized"}` (base64 std).
- `POST /api/v1/admin/directory` (requireAdmin, body `{"directory","sigs"}`, 2 MiB limit) calls signerclient.InstallDirectory.
  - Before forwarding, it takes the base from currentDirectory. If currentDirectory errors, it answers 503 `{"error":"signer unavailable"}` and forwards nothing.
  - On success it computes `newlyBound`: the canonical credential IDs present in the newly installed version (the posted directory the signer just accepted, parsed with directory.Parse) and absent from that base. newlyBound is always a subset of the installed version's credential IDs, so nothing unbound can be deleted. It then calls `serverdb.DeleteBound(newlyBound []string, nowUS int64)` and returns `{"version","sha256","leaf_index"}`. Addresses review finding 02-09-F6.
  - `DeleteBound` runs one transaction. It deletes the pending_credentials whose id is in newlyBound. For each user_name whose row it deleted, it then deletes the pending_users row only when that user has no remaining pending credential **and** the invite is not open (`invite_used_us IS NOT NULL OR invite_expires_us <= now`). It never touches a pending account whose invite is unused and unexpired, for example a directory user's open extra-passkey invite, and never another user's pending credential.
  - On a signer refusal it returns 409 for `directory_version_chain`, 403 for the other unauthorized details and 400 for `directory_invalid`, with `{"error": <signer detail>}`.
- `GET /api/v1/admin/users` (requireAdmin) returns `{"directory_version", "users":[{"name","status","credentials":[{"fingerprint","alg","synced"}]}], "pending":[{"name","invite_expires_at","invite_used","credentials":N}]}`.
- `GET /api/v1/admin/directory` and `GET /api/v1/admin/users` read the directory only through currentDirectory. On its error they answer 503 `{"error":"signer unavailable"}` and return no directory data.

**internal/directory/diff.go.** `Diff(old, new *Directory) []string` returns stable, sorted lines such as `+ user alice (active)`, `+ credential alice SHA256:… ES256 synced=false`, `~ user bob active -> disabled`, and `+/- role …`, `+/- group …`, `+/- host_group …` with their members and principals. A nil old means genesis.

**cmd/keyroster/dirpipe.go.**
- `fetchVerifiedDirectory(ctx, env cliEnv, adminKey string) (*verifiedDirectory, error)` is the one shared fetch-and-verify helper (addresses review finding 02-11-F7). `verifiedDirectory` holds `Doc, Sigs []byte; Dir *directory.Directory; Policy *trust.Policy; Signers []string; SHA256 string`. Steps 1-2 below live in it. editDirectory, `directory show|sign|install` and 02-11's `host principals` all call it, and none of them repeats the Trust/GET/Parse/VerifySignatures glue.
- `editDirectory(ctx, env cliEnv, opts editOpts, mutate func(d *directory.Directory, pol *trust.Policy) error) error`. opts holds `Yes bool`, `Out string` and `AdminKey string`. The steps:
1. (fetchVerifiedDirectory) loadConfig; serverclient.New; `Trust(cfg.TrustPins, cfg.TrustThreshold)` returns the bundle and policy.
2. (fetchVerifiedDirectory) GET /api/v1/admin/directory. When version > 0: `directory.Parse(doc)` and `directory.VerifySignatures(doc, sigs, policy)`, which must meet the quorum. On failure refuse with "the server's directory is not signed by the policy admins; refusing to build on it". When version is 0, the base is nil.
3. next = a deep copy of the base (or a new Directory with Version 1, Prev GenesisPrev and empty lists) with Version + 1 and Prev = trust.SHA256Hex(base bytes). Call mutate, then Sort, Validate and CheckPolicy.
4. Print Diff and the next version's SHA-256. Prompt `Sign directory version N? [y/N]` on the TTY unless --yes. With no TTY and no --yes, refuse.
5. Sign `next.Canonical()` with sshsig under directory.Namespace using the admin key from --admin-key or config.AdminKey, through agentSigner over dialAgent.
6. If `policy.AdminQuorum > 1` or --out is set: write `<Out>/directory.json` and `<Out>/directory.json.sigs` (armored SSHSIG blocks, newline-separated, the root sign convention) plus `<Out>/base.sha256`. Print the number of signatures present and needed and the next commands (`keyroster directory sign <Out>`, `keyroster directory install <Out>`). Otherwise POST /api/v1/admin/directory.
7. A 409 `directory_version_chain` becomes the error "the directory changed since it was read (another admin installed a version); re-run this command". That advice fits only this direct path, which rebuilds from the current base.

**cmd/keyroster/directory.go** (each subcommand gets its base from fetchVerifiedDirectory):
- `keyroster directory show` prints the verified installed directory: version, SHA-256, signers, users with credential fingerprints, roles, groups and host groups.
- `keyroster directory sign DIR`:
  1. load the proposal;
  2. verify that it parses, that its prev equals the SHA-256 of the currently installed verified directory (or that it is genesis when none is installed), and, through `checkProposalSigs(doc, sigs []byte, pol *trust.Policy) ([]string, error)`, that every existing signature parses, verifies over directory.json under directory.Namespace, and is by a policy admin. Any signature that fails any of these refuses the whole proposal. VerifySignatures only skips non-admin signers, so this check is separate (addresses review finding 02-09-F14). Nothing reaches the agent before these checks pass;
  3. print Diff against the installed base and confirm;
  4. append this admin's signature.
- `keyroster directory install DIR` first runs the same prev check against fetchVerifiedDirectory, then posts the proposal.
- Stale proposal (addresses review finding 02-09-F10): when the prev check fails in `directory sign` or `directory install`, or install gets a 409 `directory_version_chain` after the check passed, both refuse with: "the directory changed since it was read: proposal DIR is based on version N, but version M is installed. Discard DIR and re-run the command that produced it (for example `keyroster user approve NAME --fingerprint FP`)". N is the proposal's version − 1 and M the installed version. They never say "re-run this command", since posting the same stale proposal fails again.
