**DB.** `0003_web.sql` adds `web_challenges(id TEXT PRIMARY KEY, user_name TEXT NOT NULL, challenge BLOB NOT NULL, expires_us INTEGER NOT NULL)` and `sessions(id_hash BLOB PRIMARY KEY, user_name TEXT NOT NULL, cred_id BLOB NOT NULL, created_us INTEGER NOT NULL, last_seen_us INTEGER NOT NULL)`. `cred_id` is the credential that opened the session (addresses review finding 02-10-F2). db.go gains:
- `CreateChallenge`;
- `TakeChallenge(id, now)` (delete-returning; expired or absent gives ErrNotFound);
- `CreateSession(hash, user, credID, now)`;
- `TouchSession(hash, now, idle, absolute) (user string, credID []byte, err error)`;
- `DeleteSession`.

TouchSession is one conditional statement (addresses review finding 02-10-F5): `UPDATE sessions SET last_seen_us = max(last_seen_us, :now) WHERE id_hash = :hash AND :now - last_seen_us <= :idle AND :now - created_us <= :absolute RETURNING user_name, cred_id`, with named parameters (sql.Named), microsecond values for now, idle and absolute. When no row matches, it runs `DELETE FROM sessions WHERE id_hash = :hash` and returns ErrNotFound, so an expired row is never updated or revived.

**weblogin.go.**
- `GET /login` renders login.html: `<main id="kr-login" data-begin="/api/v1/web/login/begin" data-finish="/api/v1/web/login/finish">` with a username input, a submit button and a `<p role="alert">`.
- Signer state (addresses review finding 02-10-F1). Begin, finish and withSession read the RP and origins only through 02-06's `(*Server).currentStatus(ctx)`, and the directory only through 02-09's `(*Server).currentDirectory(ctx)`, which itself reads through currentStatus and fails closed. Freshness (cross-plan audit):
  - a directory installed through this server, including a disable, reaches these reads on the next request. 02-09's install handler calls 02-06's `dropStatus`, the status cache's invalidation hook, as soon as the signer answers. Every keyroster CLI edit takes this path;
  - a directory installed without this server, directly on the signer socket, reaches them within the 5 s status window. That bound is accepted (T-02-91);
  - this plan adds no signer call and never calls the hook; it only reads.

  When currentStatus or currentDirectory returns an error:
  - begin and finish answer 503 `{"error":"signer unavailable"}` and create nothing;
  - withSession renders the 02-06 error page with status 503 and renders nothing from stale data. It does not delete the session, because an outage is not a logout.
- `POST /api/v1/web/login/begin {"user"}`. The user must be active in the directory mirror with at least one credential. Otherwise answer 404 `{"error":"no usable passkey for this user"}`, identical for unknown, pending, disabled and credential-less users. Create a 32-byte challenge with a 120 s expiry and return `{"challenge_id", "publicKey": {"challenge", "allowCredentials":[{"type":"public-key","id"}], "rpId", "userVerification":"required", "timeout":60000}}` (base64url).
- `POST /api/v1/web/login/finish {"challenge_id","credential_id","authenticator_data","client_data_json","signature"}`:
  1. TakeChallenge;
  2. re-check, through currentDirectory, that the user is active and that the credential belongs to them;
  3. `webauthn.VerifyAssertion(cred, rp_id, origins, challenge, assertion)`;
  4. create a session ID (crypto/rand, 32 bytes, base64url) and store its SHA-256 with the user name and the credential ID (`CreateSession`);
  5. Set-Cookie `__Host-keyroster-session=<id>; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=43200`;
  6. return `{"redirect":"/account"}`.

  Any failure returns 401 `{"error":"sign-in failed"}` and logs the specific reason through slog.
- Logging (addresses review finding 02-10-F15). Each of these is one slog line with `event`, `user`, the client IP and a `reason` code: a successful finish (`signin_ok`), a refused finish (the specific reason), a begin 404 (`no_usable_passkey`), a 429 on begin or finish (`rate_limited`) and a logout (`logout`). A log line never holds the session ID, its hash, the challenge or the assertion. Web sign-in stays out of the signer's Merkle log: it grants no SSH access, and issuance is audited there (02-12).

**session.go.**
- `withSession(next)` reads the cookie, hashes it and calls TouchSession with idle 1 h and absolute 12 h.
  - It then calls currentStatus and currentDirectory, and fails closed as above when either errors.
  - It requires the user to still be active in that directory, and the session's `cred_id` to still be bound to that user (addresses review finding 02-10-F2). Otherwise it deletes the session.
  - A role or group change that keeps the user active and the credential bound does not end the session; /account shows the new access on the next request when the change went through this server, and within the 5 s status window otherwise.
  - It puts the user name into the request context. A missing or invalid session redirects HTML routes with 303 to /login.
  - Residuals, accepted (T-02-91):
    - A disable installed through this server (`keyroster user disable`) ends the session on its next request. Only a disable installed without the server, directly on the signer socket, can take up to the 5 s status window.
    - The check runs per request. If the user is disabled and then re-enabled, with the same credential still bound, and no request uses the session in between, the session survives. The session is read-only, ends after 1 h idle or 12 h absolute, and never authorizes issuance. An admin who needs it gone removes or replaces the credential, which ends the session on its next request.
- `POST /logout` deletes the row, sets the same cookie with Max-Age=0, and redirects 303 to /login. CrossOriginProtection from 02-06 already wraps it.

**account.go.** `GET /account` (withSession) renders account.html with:
- name, status, directory version;
- `Authorize(user, nil)`: each role with its principals and max TTL, the overall TTL cap min(role caps, user CA cap), or "no roles yet" when the user has none;
- each credential's `webauthn.Fingerprint`, its algorithm, and "synced" when backed_up, else "device-bound";
- a logout form;
- the text "Read only. Ask an admin to change roles or credentials."

**Rate limits.** ratelimit.go adds a per-username limiter next to the per-client one: begin and finish allow 20/min with burst 10 per client (02-07's `clientKey`: RemoteAddr only, IPv6 by /64), and 10/min per username. Sign-in is its own route class with 02-07's global backstop at ten times the per-client rate (200/min, burst 100).
- The per-username limiter reuses 02-07's bounded LRU limiter map (10 000 entries, idle eviction), as a second instance (addresses review finding 02-10-F6).
- It is keyed only on names that match the directory user-name rule `^[a-z0-9][a-z0-9._-]{0,63}$`. A begin with any other name gets the uniform 404 without creating a limiter entry; the per-IP limit still applies.
- Finish keys on the user name stored with the challenge, never on client input.

**app.js** gains the sign-in ceremony on `#kr-login`: begin, decode, `navigator.credentials.get({publicKey})`, then post `{challenge_id, credential_id: rawId, authenticator_data, client_data_json, signature}` (base64url) to finish, then `location.assign(redirect)`. index.html links to /login and /account.
- Error handling follows 02-08's pattern (cross-plan request, from 02-08-F16), reusing 02-08's helpers where they are factored out:
  - on load, feature-detect `window.PublicKeyCredential` and `navigator.credentials`. If either is missing, write "This browser does not support passkeys" into the `role="alert"` element and disable the button;
  - the whole begin/get/finish chain sits in one try/catch. On any failure, write the server's `error` text, or else the exception's `name` and `message`, into the alert element through `textContent` only, never by assigning markup, and re-enable the button.
