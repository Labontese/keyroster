<objective>
Make `internal/directory` `TestAuthorizeOneUser` robust against one slow wall-clock sample without weakening it as the guard for regression R1. This is a test-only change.

**Root cause.** The test (`internal/directory/directory_test.go:543-565`) times one `Validate()` of a 20000-user directory and one `Authorize()` of the last user, then fails when Authorize took more than Validate/20.
- Normally Authorize takes about 1 ms against about 73 ms for Validate. Measured on this workstation at 52b99c4: Authorize readings of 0s, 999.3µs and 1.0002ms against Validate readings of 66.6-74.2 ms.
- On cli-windows one sample was hit by a scheduler or GC stall: "Authorize of one user took 9.4551ms, Validate of 20000 users 99.4036ms" (run 39432354498, job 118660357874).
- One wall-clock sample cannot tell a stall from a regression.

**What the test guards (R1, `.planning/phases/02-passkey-login-mvp/02-03-SUMMARY.md` R1 row, commit `f35f03e`).**
- Before `f35f03e`, Authorize called `roleGrants` and built every user's roles.
- At b4b3d02 that cost 22-33 ms against a Validate of 71-88 ms, about a third of Validate.
- The signer runs Authorize under `s.mu` for every login (T-02-12). That slow Authorize must still fail the test.

**Fix (decided here, no CONTEXT.md exists).**
- **Shape.** Run 5 interleaved rounds. Each round times one Validate and then one Authorize. Compare the fastest Authorize run with the fastest Validate run, against the unchanged Validate/20 bound.
- **Fastest Authorize** discards a stalled Authorize sample. This removes the false FAIL seen on CI.
- **Validate is also measured 5 times, and its fastest run is used.** With a single Validate sample, one stall in Validate loosens the bound and can hide R1. For example, a Validate of about 700 ms gives a bound of about 35 ms, and the 22-33 ms R1 Authorize passes. That is a false PASS. The fastest of 5 is the steadiest estimate of Validate's real cost, so the comparison is fastest against fastest. Task 2 proves this.
- **Interleaving** spreads the Authorize samples over about 0.4 s instead of a few consecutive milliseconds. A period of contention therefore cannot cover all of them, for example another package's test binary running in parallel under `go test ./...` on the CI runner.
- **The Validate/20 bound is kept.** There is no measured reason to change it.
  - With the fix, Authorize sits about 3.5x under the bound (about 1 ms against about 3.5 ms).
  - Under R1 it sits about 6-7x over (22-33 ms against 3.5-4.4 ms).
- **No forced GC** before the timed calls. The fastest-of-5 already discards a sample that a GC cycle hit, and the test keeps measuring the path the signer runs.

**Timer granularity.** Go's monotonic clock on this Windows workstation advances in steps of about 1 ms (the readings above). So the fastest Authorize run often reads 0s. That is fine, because R1 is far above one step. The SUMMARY must not claim sub-millisecond precision.

Purpose: the test stops failing at random on CI, and still catches an Authorize that computes every user's roles.
Output: one signed test commit, one signed docs commit (this plan and its SUMMARY), and an open keyroster-bot PR without auto-merge, with green required checks.
</objective>
